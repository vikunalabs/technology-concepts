# Quartz Scheduler — From Basics to Advanced

**Version baseline:** this guide targets **Spring Boot 4.x** and the **Quartz 2.5.x** line that Spring Boot 4.x's `spring-boot-starter-quartz` pulls in transitively (confirmed against Maven Central for `spring-boot-starter-quartz` 4.0.0/4.1.0). Code involving `QuartzAutoConfiguration`, `SchedulerFactoryBeanCustomizer`, `@QuartzDataSource`, and the `spring.quartz.*` property namespace assumes this baseline — notably, the autoconfiguration package itself is `org.springframework.boot.quartz.autoconfigure` in Boot 4.x, which moved from `org.springframework.boot.autoconfigure.quartz` in Boot 3.x. If you're on Spring Boot 3.x, the concepts throughout this guide still apply, but check that import path, and confirm your project's actual resolved Quartz version (e.g. via `mvn dependency:tree` or `./gradlew dependencies`) rather than assuming it matches exactly.

## Part 1 — Foundations

### 1.1 What Quartz actually is

Quartz is a standalone Java scheduling library. It existed long before Spring, before dependency injection was standard, before most of the frameworks you use today. This matters more than it sounds like it should — a lot of Quartz's design (its default instantiation model, its data-map-of-strings mentality) makes much more sense once you remember it was built to work in *any* Java application, not just Spring ones.

At its core, Quartz answers one question: **"run this piece of code, at this time (or these times)."** Everything else — clustering, persistence, misfire handling, listeners — exists in service of that one job.

### 1.2 The four core concepts

| Concept | What it is | Analogy |
|---|---|---|
| **Job** | The actual work to perform — a class implementing `org.quartz.Job` | A recipe |
| **JobDetail** | Metadata describing a Job: its class, identity, data, durability | A recipe card with notes |
| **Trigger** | *When* to fire a JobDetail — cron expression, simple interval, etc. | An alarm clock |
| **Scheduler** | The engine that ties triggers to jobs and fires them | The kitchen, running everything |

The critical relationship: **a `JobDetail` is not a `Job` instance.** It's a *description* of one. Quartz creates a fresh `Job` instance every time a trigger fires (more on this in Part 3 — it's the source of a very common integration bug). Multiple `Trigger`s can point at the same `JobDetail`, each firing it on a different schedule.

```java
public class HelloWorldJob implements Job {
    @Override
    public void execute(JobExecutionContext context) throws JobExecutionException {
        System.out.println("Hello, Quartz!");
    }
}
```

That's the entire contract: implement `execute()`. Quartz calls it; you do work; you throw `JobExecutionException` if something goes wrong.

### 1.3 Identity: name + group

Every `JobDetail` and every `Trigger` has an identity made of a **name** and a **group** — two strings, together forming a `JobKey` or `TriggerKey`. Groups exist so you can namespace and bulk-operate on related jobs ("pause the entire `order-export` group") without every job needing a globally unique name.

```java
JobDetail job = JobBuilder.newJob(HelloWorldJob.class)
        .withIdentity("myJob", "myGroup")
        .build();
```

If you don't specify a group, Quartz uses `"DEFAULT"`. If your system has more than one kind of scheduled work, it's worth deciding on real group names from the start rather than leaving everything in `"DEFAULT"` — because changing a job's or trigger's group later means recreating its identity, not just editing a setting. A `JobKey`/`TriggerKey` is the combination of name *and* group, so switching an existing job from `"DEFAULT"` to some other group means it becomes a different key entirely — you'd need to delete the old one and reschedule under the new identity, rather than simply relabeling it in place.

### 1.4 Building and scheduling, end to end

```java
public class QuartzBasicsApplication {
    public static void main(String[] args) throws SchedulerException {
        // 1. Get a scheduler
        Scheduler scheduler = new StdSchedulerFactory().getScheduler();
        scheduler.start();
        
        // 2. Build a JobDetail
        JobDetail job = JobBuilder.newJob(HelloWorldJob.class)
                .withIdentity("helloWorldJob", "helloWorldGroup")
                .build();
        
        // 3. Build a Trigger
        Trigger trigger = TriggerBuilder.newTrigger()
                .withIdentity("helloWorldTrigger", "helloWorldGroup")
                .startNow()
                .withSchedule(SimpleScheduleBuilder.simpleSchedule()
                        .withIntervalInSeconds(10)
                        .repeatForever())
                .build();
        
        // 4. Schedule the job
        scheduler.scheduleJob(job, trigger);
        
        // 5. Keep the application running
        Thread.currentThread().join();
    }
}
```

The typical flow: get a scheduler → build a `JobDetail` → build a `Trigger` → schedule them together → start the scheduler. That last step is the one exception to treating this as a strict sequence — starting the scheduler can happen before or after building/scheduling the job and trigger; what actually matters is only that nothing fires until `start()` has been called.

### 1.5 Job Data: Passing parameters to your job

Real-world jobs need data: an order region, an email address, a file path. Quartz provides `JobDataMap` — a `Map<String, Object>`-like structure attached to both `JobDetail` and `Trigger`.

**Setting job data:**
```java
JobDetail job = JobBuilder.newJob(HelloWorldJob.class)
        .withIdentity("helloWorldJob", "helloWorldGroup")
        .usingJobData("message", "Hello World from Quartz!")
        .usingJobData("timestamp", String.valueOf(System.currentTimeMillis()))
        .build();
```

**Retrieving job data in your `execute()` method:**
```java
public class HelloWorldJob implements Job {
    private static final Logger log = LoggerFactory.getLogger(HelloWorldJob.class);
    
    @Override
    public void execute(JobExecutionContext context) throws JobExecutionException {
        try {
            // Access merged job data (JobDetail + Trigger data)
            JobDataMap dataMap = context.getMergedJobDataMap();
            String message = dataMap.getString("message");
            String timestamp = dataMap.getString("timestamp");
            
            log.info("Executing job: {}", message);
            log.info("Job scheduled at: {}", timestamp);
            
            // Your business logic
            System.out.println("Printing: " + message);
            
        } catch (Exception e) {
            log.error("Error executing job", e);
            throw new JobExecutionException("Job execution failed", e);
        }
    }
}
```

**Important:** `getMergedJobDataMap()` combines data from both the `JobDetail` and the `Trigger`. If the same key exists in both, the trigger's value takes precedence. Alternatively, you can access them separately:
- `context.getJobDetail().getJobDataMap()` — job-level data only
- `context.getTrigger().getJobDataMap()` — trigger-level data only

**Type safety:** Use the appropriate getter for your data type — `getString()`, `getLong()`, `getInt()`, `getBoolean()`, etc. The exact failure mode for a mismatched getter depends on the stored value's actual type and the getter used — sometimes a straightforward `ClassCastException`, sometimes a conversion error — so don't rely on a specific exception type in a catch block; instead, make sure the getter you call always matches how the value was actually stored.

### 1.6 Graceful Shutdown: Why it matters and how to do it

If your application exits while a job is executing, that job may be interrupted mid-flight. Worse, if you're using a persistent job store (Part 5), you may leave the scheduler in an inconsistent state.

**The solution: a JVM shutdown hook:**
```java
public class QuartzBasicsApplication {
    private static final Logger log = LoggerFactory.getLogger(QuartzBasicsApplication.class);

    public static void main(String[] args) throws SchedulerException {
        Scheduler scheduler = new StdSchedulerFactory().getScheduler();
        scheduler.start();
        
        // Schedule your job...
        
        // Register shutdown hook
        Runtime.getRuntime().addShutdownHook(new Thread(() -> {
            try {
                log.info("Shutting down scheduler...");
                scheduler.shutdown(true);  // true = wait for running jobs to finish
                log.info("Scheduler shutdown complete");
            } catch (SchedulerException e) {
                log.error("Error shutting down scheduler", e);
            }
        }));
        
        // Keep the main thread alive
        Thread.currentThread().join();
    }
}
```

The `shutdown(true)` parameter is critical, and it's worth being precise about what each value actually does — checked directly against Quartz's own documentation:
- `true` — the call blocks and won't return until all currently executing jobs have completed
- `false` — the call returns immediately; the scheduler stops accepting new firings, but **any job already running keeps running to completion on its own thread.** Quartz does not interrupt it.

That second point is easy to get wrong, so it's worth stating plainly: **`shutdown(false)` does not stop a running job.** It has no mechanism to forcibly halt arbitrary Java code — if a job is stuck in `while (true) { }` or blocked on a slow network call, `shutdown(false)` returning doesn't touch it; that thread keeps running until it finishes on its own, is killed by the JVM exiting, or (separately) is interrupted via `Scheduler.interrupt(...)` — and even that only works if the job class implements `InterruptableJob` and actually checks for the interrupt itself.

Choose between `true` and `false` based on whether waiting matters to you, not based on any expectation that `false` cuts a job off: `true` is for when you need the application to actually pause until in-flight work is done (e.g. before a deploy); `false` is for when you don't want to wait, accepting that already-running jobs finish independently, off in the background, after `shutdown()` has already returned.

**Note if you're heading toward Spring Boot:** this manual shutdown hook is the *plain Quartz* way of doing this — appropriate for the `StdSchedulerFactory` setup shown in Parts 1–2. Once Spring Boot's autoconfiguration is managing the scheduler (from Part 3 onward), it already participates in Spring's own application shutdown lifecycle, and the same "wait for jobs to finish" behavior becomes a one-line property instead of a hand-written hook — see Part 8.5.

### 1.7 Before going further: do you actually need Quartz?

Worth answering before investing in everything the rest of this guide covers. Spring itself ships a much simpler scheduling mechanism — `@Scheduled` — and for a real slice of use cases, it's the better choice, not a lesser one. The two solve overlapping but genuinely different problems:

| Requirement | `@Scheduled` | Quartz |
|---|---|---|
| Simple recurring task, one instance of the app | ✅ — a single annotated method, no infrastructure | Works, but is more machinery than the job needs |
| Schedule must survive an application restart | ❌ — defined in code, not persisted anywhere | ✅ (Part 5) |
| Multiple application instances, one coordinated firing owner per trigger | ❌ — every instance runs it independently, no coordination | ✅ (Part 6) — coordinated, not a strict exactly-once guarantee; misfire catch-up, cluster recovery, and manual re-triggering can all still produce a repeat execution (Part 10) |
| Schedule needs to change at runtime without a redeploy | ❌ — the schedule is a compile-time annotation value (or a property it reads once) | ✅ (Part 9) |
| Pause/resume a schedule on demand | ❌ | ✅ (Part 9.4) |
| Per-firing metadata (job data, misfire policy, recovery behavior) | ❌ — no equivalent concept | ✅ (Parts 1.5, 2.2, 2.3) |
| Per-tenant or database-driven schedules | ❌ — not what it's built for | ✅ (Part 9.3) |

If your need is "run this method every 15 minutes, in a single-instance application, defined once in code" — `@Scheduled` is less to learn, less to configure, and nothing about Quartz makes that simpler. The moment persistence, clustering, runtime-changeable schedules, or per-firing metadata enters the picture, that's the point where `@Scheduled` genuinely runs out of road and Quartz's extra weight starts paying for itself. This guide assumes you've already landed on "I need Quartz" for one of those reasons — if you haven't yet, it's worth confirming that before working through the rest of it.

## Part 2 — Triggers in Depth

**A note on what changes from here:** everything in Parts 1–2 uses plain Quartz — `new StdSchedulerFactory().getScheduler()`, no Spring involved at all. Starting in Part 3, the tutorial shifts to a Spring Boot application, where a `Scheduler` is autoconfigured for you from `JobDetail`/`Trigger` beans instead of built by hand. Everything about triggers, misfires, and the job model covered in this Part still applies identically either way — only *how the scheduler itself gets constructed and started* changes.

### 2.1 SimpleTrigger vs CronTrigger

These are the two trigger types you'll encounter most often.

**`SimpleTrigger`** — fire once, or repeat at a fixed interval, a fixed number of times (or forever):
```java
SimpleScheduleBuilder.simpleSchedule()
        .withIntervalInMinutes(5)
        .repeatForever();
```

**`CronTrigger`** — fire according to a cron expression, for calendar-based schedules ("every weekday at 9am", "the 1st of every month"):
```java
CronScheduleBuilder.cronSchedule("0 0 9 ? * MON-FRI");
```

Quartz cron expressions have **six required fields, plus an optional seventh** — not 5 or 6 like Unix cron. This trips up almost everyone the first time:

```
seconds  minutes  hours  day-of-month  month  day-of-week  [year]
   0        0        9        ?          *        MON-FRI
```

The `?` is Quartz-specific: it means "no specific value," and it's valid only in the `day-of-month` or `day-of-week` field. In practice, you'll almost always use it in whichever of those two fields *isn't* carrying the actual scheduling constraint for a given trigger — since Quartz's convention is that only one of these two fields drives the schedule at a time, the other is left as `?` to defer to it.

### 2.2 Misfires — the concept most people skip and later regret

A **misfire** happens when a trigger's scheduled fire time passes without it actually firing — because the scheduler was down, all worker threads were busy, or the previous firing of a `@DisallowConcurrentExecution` job was still running.

Every trigger type has a **misfire instruction** governing what happens next. For `CronTrigger`, the two you'll actually use:

- `withMisfireHandlingInstructionFireAndProceed()` — fire once immediately to "catch up," then resume the normal schedule.
- `withMisfireHandlingInstructionDoNothing()` — skip the missed firing entirely, wait for the next naturally scheduled time.

```java
Trigger trigger = TriggerBuilder.newTrigger()
        .withIdentity("myTrigger", "myGroup")
        .withSchedule(CronScheduleBuilder.cronSchedule("0 0 9 * * ?")
                .withMisfireHandlingInstructionFireAndProceed())
        .build();
```

There's no universally "correct" choice — it depends on whether a missed firing represents lost work that must happen eventually, or a snapshot that's only meaningful at its exact scheduled moment. A "generate today's export batch" job usually wants `FireAndProceed` (the export still needs to happen); a "sample current queue depth every minute" job usually wants `DoNothing` (a late sample of a now-different queue depth isn't useful). **Pick deliberately per job — don't leave it at Quartz's default and hope.**

### 2.3 `storeDurably` and `requestRecovery`

Two `JobBuilder` flags that matter far more than their one-line names suggest:

```java
JobDetail job = JobBuilder.newJob(HelloWorldJob.class)
        .withIdentity("myJob", "myGroup")
        .storeDurably(true)
        .requestRecovery(true)
        .build();
```

- **`storeDurably(true)`** — by default, Quartz deletes a `JobDetail` from its store once it has no triggers pointing at it. Whether that's a problem depends on how your job's lifecycle actually works. If the `JobDetail` is meant to exist independently of any particular trigger — you plan to add/remove/reschedule triggers against it dynamically over time (Part 9) — then losing the definition the moment it briefly has zero triggers is a real footgun, and `storeDurably(true)` is what you want. But if a `JobDetail` and its trigger are always created and torn down together, and the `JobDetail` genuinely has no reason to exist without that trigger, non-durable (the default) is perfectly legitimate — there's nothing left to accidentally lose. Use `storeDurably(true)` when the `JobDetail` should be able to outlive having zero triggers; leave it `false` when it shouldn't.
- **`requestRecovery(true)`** — if the scheduler process dies *mid-execution* of this job, should Quartz re-run it on restart? This only matters for jobs where "started but didn't finish" leaves things in a state that's safe (or necessary) to redo — it should line up with whether your job's own logic is idempotent/restart-safe, not be flipped on reflexively for every job. Worth noting it's set on the `JobBuilder`, not the `TriggerBuilder`, above — recovery is a property of the *job* ("should this kind of work be redone if interrupted"), not of any one particular firing's timing, which is why it belongs to the `JobDetail` rather than to a specific `Trigger`.

### 2.4 Complete Example with Misfire Handling and Shutdown

Here's a complete, standalone Quartz example combining everything from Parts 1-2 — complete in the sense of showing every piece wired together end-to-end, though a real production application would also add proper application lifecycle management, externalized configuration, and the Spring Boot integration covered starting in Part 3, rather than a bare `main()` method:

```java
public class QuartzBasicsApplication {
    private static final Logger log = LoggerFactory.getLogger(QuartzBasicsApplication.class);
    
    public static void main(String[] args) {
        try {
            Scheduler scheduler = new StdSchedulerFactory().getScheduler();
            scheduler.start();
            log.info("Scheduler started successfully");
            
            // Build JobDetail with data
            JobDetail job = JobBuilder.newJob(HelloWorldJob.class)
                    .withIdentity("helloWorldJob", "helloWorldGroup")
                    .usingJobData("message", "Hello World from Quartz!")
                    .usingJobData("timestamp", String.valueOf(System.currentTimeMillis()))
                    .storeDurably(true)
                    .requestRecovery(true)
                    .build();
            
            // Build Trigger with misfire handling
            Trigger trigger = TriggerBuilder.newTrigger()
                    .withIdentity("helloWorldTrigger", "helloWorldGroup")
                    .startNow()
                    .withSchedule(SimpleScheduleBuilder.simpleSchedule()
                            .withIntervalInSeconds(25)
                            .repeatForever()
                            .withMisfireHandlingInstructionFireNow())
                    .build();
            
            scheduler.scheduleJob(job, trigger);
            log.info("Job scheduled successfully");
            
            // Graceful shutdown
            Runtime.getRuntime().addShutdownHook(new Thread(() -> {
                try {
                    log.info("Shutting down scheduler...");
                    scheduler.shutdown(true);
                    log.info("Scheduler shutdown complete");
                } catch (SchedulerException e) {
                    log.error("Error shutting down scheduler", e);
                }
            }));
            
            Thread.currentThread().join();
            
        } catch (SchedulerException e) {
            log.error("Failed to initialize or start scheduler", e);
            System.exit(1);
        } catch (InterruptedException e) {
            log.error("Main thread interrupted", e);
            Thread.currentThread().interrupt();
        }
    }
}
```

**Key takeaways from this example:**
1. **Job data** passes configuration to the job
2. **Misfire handling** ensures missed firings are caught up
3. **Shutdown hook** guarantees graceful cleanup
4. **Error handling** prevents silent failures

### 2.5 Trigger lifecycle states

There are two different sets of "trigger state" worth knowing, and conflating them leads to a real problem: code that calls `Scheduler.getTriggerState(triggerKey)` and expects to see something it will never actually return.

**The public API** — what `Scheduler.getTriggerState()` actually returns, checked directly against the `Trigger.TriggerState` enum's javadoc — has exactly six values:

| State | Meaning |
|---|---|
| `NONE` | No trigger exists with the given key |
| `NORMAL` | The ordinary resting state — scheduled, waiting for its next fire time, nothing unusual going on |
| `PAUSED` | Explicitly paused via `pauseTrigger`/`pauseJob`/`pauseAll` (Part 9.4) |
| `COMPLETE` | A one-time trigger (or the final firing of a finite one) has finished and won't fire again |
| `ERROR` | The trigger encountered a problem serious enough that Quartz stopped trying to fire it normally (e.g. a persistent misfire situation past a configured threshold) |
| `BLOCKED` | The trigger's `JobDetail` is `@DisallowConcurrentExecution` (Part 7.1) and another execution of it is already running — this trigger is ready to fire but held back until that execution finishes |

**Internally**, the JDBC job store additionally tracks finer-grained states while it coordinates acquisition and execution across a cluster — commonly including `WAITING`, `ACQUIRED`, `EXECUTING`, and `PAUSED_BLOCKED` — but these are implementation detail, not something `getTriggerState()` (or any other public API) exposes to your code. Different job store implementations can and do model this internal bookkeeping differently. If you're writing code against the `Scheduler` API, the six-value public enum above is the complete set you'll ever actually see; the internal states are only useful as a mental model for *why* a trigger transitions the way it does.

The one worth internalizing on first read is `BLOCKED`, since it's the mechanism behind `@DisallowConcurrentExecution`'s behavior from Part 7.1: it isn't that Quartz silently drops or ignores a firing that arrives while the job is still running — the trigger genuinely reports as `BLOCKED`, sits there for the duration of the in-progress execution, and then becomes eligible to fire again (back to `NORMAL`) once the running execution completes and the `JobDetail` is no longer occupied. Internally, a JDBC job store's firing typically moves through something like `WAITING → ACQUIRED → EXECUTING` while this happens — but what your own code should reason about, and the only thing `getTriggerState()` will ever hand back, is the public six-value enum above.

## Part 3 — Job Instantiation and the JobFactory

This is the single most common integration failure when wiring Quartz into a Spring Boot application, so it gets its own Part — and because it trips up so many people, this Part starts with a quick primer on the Spring concepts involved, for anyone newer to Spring. If you're already comfortable with beans, dependency injection, and autoconfiguration, skip straight to 3.1.

### 3.0 A quick primer: Beans, the ApplicationContext, and Dependency Injection

**A Spring "bean"** is just an object — but instead of your code creating it directly with `new SomeClass()`, Spring creates it for you and manages it. Why bother? Because it lets Spring wire objects together automatically instead of you doing it by hand everywhere.

**The `ApplicationContext`** is the container that holds all of these beans for the lifetime of your running application. When your Spring Boot app starts up, it builds one big `ApplicationContext`, populates it with every bean your app defines (plus a large number of beans Spring Boot itself provides), and keeps it alive until the app shuts down. Anything that needs a bean asks the `ApplicationContext` for it — directly, or (much more commonly) indirectly, through dependency injection.

**Dependency injection (DI)** is the mechanism by which one bean gets access to another. Say you have a class that needs a database-access helper:

```java
public class OrderExportService {

    private final OrderRepository orderRepository;

    // This is "constructor injection" — the dependency arrives as a
    // constructor parameter instead of being created inside the class.
    public OrderExportService(OrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }
}
```

`OrderExportService` never calls `new OrderRepository()` itself. Instead, when Spring builds the `OrderExportService` bean, it looks at the constructor, sees it needs an `OrderRepository`, finds the `OrderRepository` bean already sitting in the `ApplicationContext` (or builds it first, if it hasn't yet), and passes it in automatically. This is "inversion of control" — the class doesn't control how its dependencies are constructed; the container does.

**How does a class become a bean in the first place?** Two common ways:

1. **`@Component`** (and its more specific variants `@Service`, `@Repository`, `@Controller`) — you annotate the class itself. At startup, Spring scans your codebase for these annotations and registers each one as a bean.
   ```java
   @Component
   public class OrderExportService { ... }
   ```
2. **`@Configuration` + `@Bean`** — for objects you don't control the source of (a third-party class, or something that needs custom construction logic), you write a method that builds and returns the object, inside a class annotated `@Configuration`:
   ```java
   @Configuration
   public class MyConfig {
       @Bean
       public DataSource dataSource() {
           return DataSourceBuilder.create().build();
       }
   }
   ```
   The method's return value becomes a bean, registered under the method name (`dataSource`) by default.

**Spring Boot autoconfiguration** is a large collection of pre-written `@Configuration` classes, shipped inside Spring Boot's own libraries, that automatically set up common infrastructure — a `DataSource`, a web server, a Quartz `Scheduler` — based on what's on your classpath and what you've set in `application.properties`. This is why adding `spring-boot-starter-quartz` as a dependency and setting a couple of properties is enough to get a working, persistent, clustered scheduler without writing that plumbing yourself. Autoconfiguration classes very often use `@ConditionalOnMissingBean` — meaning "only create this bean if the application hasn't already defined its own bean of this type" — which is precisely the escape hatch that lets you override any single piece of the autoconfigured setup just by defining your own bean.

With that vocabulary in hand, the rest of this Part will make a lot more sense.

### 3.1 Quartz creates a new job instance every time a trigger fires

Recall from Part 1: a `JobDetail` is a *description* of a job — the class to run, plus some metadata — not an actual instance of it. Every single time a trigger fires, Quartz creates a **brand-new instance** of the job class to execute. This is deliberate: it keeps jobs stateless by default, so one firing's in-progress state can never accidentally leak into another firing.

This matters immediately once Spring is involved, because **Quartz has absolutely no idea what an `ApplicationContext` or a "bean" is.** Quartz predates Spring, and was designed to work in any Java application — plain, Spring-based, Jakarta EE, whatever. So when it needs a new job instance, it doesn't ask Spring for one. It uses its own internal mechanism, called a `JobFactory`.

### 3.2 The default `JobFactory`: `SimpleJobFactory`

Quartz's default `JobFactory` implementation is `SimpleJobFactory`, and it does the simplest possible thing — plain Java reflection, calling the class's no-argument constructor:

```java
// conceptually what SimpleJobFactory does
Class<? extends Job> jobClass = bundle.getJobDetail().getJobClass();
return jobClass.getDeclaredConstructor().newInstance(); // calls the no-arg constructor
```

No Spring context is consulted. No dependency injection happens. It's exactly as if you'd written `new HelloWorldJob()` yourself, somewhere deep inside Quartz's internals.

For a job class with no dependencies, that's perfectly fine:

```java
public class HelloWorldJob implements Job {
    @Override
    public void execute(JobExecutionContext context) {
        System.out.println("Hello, Quartz!");
    }
}
```

`HelloWorldJob` has an implicit no-arg constructor (Java gives you one for free when you don't declare any constructor), so `SimpleJobFactory` can build it without any trouble.

### 3.3 Why this breaks for any real Spring job class

Real jobs almost always need something injected — a service, a repository, a client for some external system. Using the dependency-injection style from 3.0:

```java
@Component
public class OrderExportJob implements Job {

    private final OrderExportService orderExportService;

    public OrderExportJob(OrderExportService orderExportService) {
        this.orderExportService = orderExportService;
    }

    @Override
    public void execute(JobExecutionContext context) {
        orderExportService.exportPendingOrders();
    }
}
```

Look closely: **this class has no no-argument constructor.** It can't — `orderExportService` has to come from somewhere, and the only constructor declared requires it as a parameter. `SimpleJobFactory.newInstance()` calls `jobClass.getDeclaredConstructor()` looking for a zero-parameter constructor to invoke — and there isn't one. It throws `NoSuchMethodException`.

Here's the part that makes this an especially nasty bug to run into for the first time: **this failure does not happen at application startup.** Spring Boot boots up fine. The `@Component`-annotated `OrderExportJob` becomes a bean just like any other, fully constructed with its dependency injected, sitting happily in the `ApplicationContext`. The `JobDetail` and `Trigger` beans register fine too. Everything looks completely healthy in your logs.

The failure only happens **the first time a trigger actually fires** — because that's the one moment Quartz reaches past Spring entirely and tries to build its *own*, second, separate instance of `OrderExportJob` using plain reflection, completely unaware that a perfectly good, fully-wired instance already exists in the `ApplicationContext`. If your schedule doesn't fire until hours (or days) after deployment, you won't find out about this until then.

### 3.4 Spring's answer: `SpringBeanJobFactory` — what it actually does, and doesn't

Spring ships its own `JobFactory` implementation, `SpringBeanJobFactory`, specifically to bridge this gap. It's tempting to assume dropping this in solves the whole problem — but it's worth being precise about what it actually does, because it's less than you might expect.

Checked directly against the Spring Framework source (`SpringBeanJobFactory.createJobInstance`, which delegates to its parent `AdaptableJobFactory`), it does exactly **two** things:

1. **Instantiates the job** — via the no-argument constructor. This is still the *only* instantiation path — identical to `SimpleJobFactory` in this respect.
2. **Populates bean properties from job/trigger data** — after instantiation, for any setter-style property on the object that matches a key in the scheduler context, job data map, or trigger data map, it sets that property's value.

That second point deserves an example, since "populates bean properties" is a fairly abstract phrase. Suppose a job class exposes a plain setter:

```java
public class SomeJob implements Job {
    private String recipientEmail; // no injected dependency, just a plain field

    public void setRecipientEmail(String recipientEmail) {  // a "bean property" setter
        this.recipientEmail = recipientEmail;
    }

    @Override
    public void execute(JobExecutionContext context) { ... }
}
```

If the job's `JobDataMap` contains a key `"recipientEmail"`, `SpringBeanJobFactory` will call `setRecipientEmail(...)` with that value after constructing the instance. This is a genuinely useful feature — but notice what it is *not*: it is not dependency injection in the Spring sense. It doesn't look anything up in the `ApplicationContext`. It's just Quartz's own data (job data map entries) being copied onto matching setter methods by name, using a Java Beans convention that long predates Spring.

**Crucially: `SpringBeanJobFactory` never checks the `ApplicationContext` for an existing bean, and it never does constructor injection.** For `OrderExportJob` from 3.3, `SpringBeanJobFactory` fails in *exactly* the same way `SimpleJobFactory` does — there's still no no-arg constructor for it to call, and `orderExportService` isn't a "bean property" that any job/trigger data map entry could satisfy anyway (it's a constructor parameter, not a setter).

### 3.5 A tempting but flawed fix: return the existing Spring bean

Before landing on the right answer, it's worth walking through the *wrong* one, because it's the version that looks correct at first glance and is genuinely common to see in the wild:

```java
// DON'T do this — see below for why
@Component
public class AutowiringSpringBeanJobFactory extends SpringBeanJobFactory
        implements ApplicationContextAware {

    private ApplicationContext applicationContext;

    @Override
    public void setApplicationContext(ApplicationContext applicationContext) {
        this.applicationContext = applicationContext;
    }

    @Override
    protected Object createJobInstance(TriggerFiredBundle bundle) throws Exception {
        Class<?> jobClass = bundle.getJobDetail().getJobClass();
        if (applicationContext.getBeanNamesForType(jobClass).length > 0) {
            return applicationContext.getBean(jobClass);   // returns the SAME instance every time
        }
        return super.createJobInstance(bundle);
    }
}
```

This looks reasonable: `OrderExportJob` is `@Component`-annotated, so it's already a fully-constructed Spring bean sitting in the `ApplicationContext` with `orderExportService` injected — why not just hand that back?

**Because `@Component` beans are singletons by default, and `applicationContext.getBean(jobClass)` returns that same singleton instance every single time it's called.** Every trigger firing — today, tomorrow, next year — gets back the *exact same object*. That directly contradicts the lifecycle guarantee established in 3.1: "Quartz creates a new job instance every time a trigger fires." This factory quietly replaces that guarantee with a different one — "Spring creates one instance at startup, and Quartz reuses it forever" — without the job class's author necessarily knowing that trade happened.

Why does that matter in practice, beyond being conceptually inconsistent? Because it's a trap waiting for whoever edits this class next. Nothing about `@Component` or `implements Job` stops someone from later adding mutable instance state:

```java
@Component
public class OrderExportJob implements Job {
    private final OrderExportService orderExportService;
    private ExportBatch currentBatch;   // added later, looks innocent

    @Override
    public void execute(JobExecutionContext context) {
        currentBatch = orderExportService.startBatch();
        // ...
    }
}
```

With the default `SimpleJobFactory` (3.2), each firing gets its own instance, so `currentBatch` would be scoped to that one execution regardless. With the singleton-returning factory above, `currentBatch` is now **shared, mutable state across every concurrent and sequential execution of this job** — exactly the kind of subtle, hard-to-reproduce bug that only shows up under real concurrency, long after the code was written and reviewed. `@DisallowConcurrentExecution` (Part 7) prevents *overlapping* executions of the same `JobDetail`, but does nothing to stop this kind of state leaking from one execution into the next sequential one.

### 3.6 The actual fix: a new instance, every time, with real dependency injection

The right building block is a different method on `AutowireCapableBeanFactory`: `createBean(Class<T> beanClass)`. Checked directly against Spring's `AbstractAutowireCapableBeanFactory` source, this method resolves the class's constructor, autowires its parameters against beans in the `ApplicationContext`, applies field/setter autowiring, and runs applicable `BeanPostProcessor`s — Spring's bean instantiation, dependency injection, initialization, and post-processing pipeline, though **not** the normal `ApplicationContext`-managed bean lifecycle (more on that distinction below) — but critically, it does this **fresh, every time it's called**, returning a brand-new, unmanaged instance rather than a shared singleton pulled from the container.

```java
@Component
public class AutowiringSpringBeanJobFactory extends SpringBeanJobFactory
        implements ApplicationContextAware {

    private AutowireCapableBeanFactory beanFactory;

    @Override
    public void setApplicationContext(ApplicationContext applicationContext) {
        this.beanFactory = applicationContext.getAutowireCapableBeanFactory();
    }

    @Override
    protected Object createJobInstance(TriggerFiredBundle bundle) throws Exception {
        Class<?> jobClass = bundle.getJobDetail().getJobClass();
        return beanFactory.createBean(jobClass);
    }
}
```

> ⚠️ **This factory intentionally replaces `SpringBeanJobFactory`'s `JobDataMap`/trigger-data property population.** Jobs using it should read scheduling parameters from `JobExecutionContext` rather than expecting them to be injected as bean properties. Details below.

This override completely replaces `SpringBeanJobFactory.createJobInstance()` rather than calling `super.createJobInstance(bundle)` — which means the setter-based `JobDataMap`/trigger-data property population described in 3.4 (Spring populating any bean property that matches a job/trigger data key) **no longer happens.** This factory only does constructor and field/setter *dependency* injection — it does not also copy `JobDataMap` values onto matching setters the way plain `SpringBeanJobFactory` does. In practice this is rarely a real loss, because the pattern used consistently throughout this guide (Part 1.5, Part 4) reads scheduling parameters by pulling them from `context.getMergedJobDataMap()` inside `execute()`, not by having Spring push them onto setter properties — so nothing in this guide's own examples actually depends on the capability being removed. But if you're used to the setter-injection style from 3.4, or you're integrating with code that relies on it, know that this factory doesn't support it. For predictable behavior with this factory, always retrieve scheduling parameters from `JobExecutionContext.getMergedJobDataMap()` rather than expecting them to appear on bean properties.

That's the whole implementation — genuinely simpler than the flawed version in 3.5, because there's no branching. `createBean(jobClass)` handles every case uniformly:

- **Constructor injection** (`OrderExportJob(OrderExportService orderExportService)`) — resolves `orderExportService` from the `ApplicationContext` and calls the constructor with it, for a fresh instance.
- **No dependencies at all** (`HelloWorldJob`) — calls the no-arg constructor, same as before.
- **Field/setter `@Autowired`** — applied automatically as part of the same pipeline.

Every one of these produces a **new object on every call**, matching Quartz's own execution model exactly instead of working around it.

**A second consequence of "not the normal `ApplicationContext`-managed bean lifecycle":** don't expect Spring's singleton destruction callbacks (`@PreDestroy`, `DisposableBean`) to run for job instances created this way. Spring exposes a matching `destroyBean(Object)` method for objects created via `createBean()`, but nothing calls it automatically here — Quartz has no reason to, since as far as it's concerned this is just a `Job` instance whose `execute()` method finished. If a job class needs cleanup after each execution, do it explicitly at the end of `execute()` rather than relying on a Spring lifecycle callback that won't fire.

**Important consequence: `OrderExportJob` should *not* be annotated `@Component`.** This reverses what earlier drafts of this tutorial taught, so it's worth being explicit about why. `createBean(Class)` works directly from the `.class` reference — it doesn't need the job class to be pre-registered as a bean at all; it only needs the job class's *dependencies* (`OrderExportService`) to be beans, which they already are via their own `@Component`/`@Service` annotations. If you *also* mark `OrderExportJob` itself `@Component`, component-scanning will build a second, separate singleton instance of it at application startup — one that just sits in the `ApplicationContext` unused, since the factory never asks the container for an existing instance anymore. That's not dangerous, just pointless — an unused bean and mild startup overhead for nothing. Leave job classes as plain, non-`@Component` classes; let `AutowiringSpringBeanJobFactory` be their only path into existence.

### 3.6a Three Spring integration approaches, side by side

The custom factory above isn't the only supported way to bridge Spring and Quartz — it's worth knowing the alternatives exist and why this guide picked the one it did:

| Approach | Constructor injection | `JobDataMap` → setter injection | Best for |
|---|---|---|---|
| Default `SpringBeanJobFactory` (3.4) | ❌ | ✅ | Simple jobs with no-arg constructors and a few setter-style parameters |
| `QuartzJobBean` (Spring's own base class for Quartz jobs) | ❌ (setter-oriented) | ✅ | Traditional Spring+Quartz style, predating widespread constructor-injection convention |
| `AutowiringSpringBeanJobFactory` via `createBean()` (3.6) | ✅ | ❌ (unless added back explicitly) | Modern, constructor-injected jobs — this guide's convention throughout |

None of these is universally "correct" — they represent different trade-offs between injection style and `JobDataMap` ergonomics. This guide standardizes on the third because it matches modern Spring's preference for constructor injection, but if you're maintaining an older Spring+Quartz codebase built around `QuartzJobBean`, that's a legitimate, still-supported alternative, not something you need to migrate away from just because this guide picked differently.

### 3.7 Spring service vs. Quartz job: two different lifecycles, on purpose

This is worth stating as its own principle, since it's the conceptual core of everything in 3.5–3.6: a Spring-managed service and a Quartz job are supposed to have *different* lifecycles, and that's a feature, not a gap to paper over.

| | Typical lifecycle | Why |
|---|---|---|
| `OrderExportService` (`@Service`) | Singleton — one instance for the whole application | It's stateless business logic; sharing one instance is efficient and safe |
| `OrderExportJob` (`implements Job`) | New instance per trigger firing | Each execution should start clean, with no state carried over from the last one |

Spring can — and, per 3.6, should — construct and inject dependencies into the job instance. That's independent of whether the job instance itself is a long-lived singleton. Dependency injection and object lifetime are two separate concerns; conflating them (as the singleton-returning factory in 3.5 does) is what caused the problem in the first place.

Worth being explicit about one thing: none of this — the custom factory, `createBean()`, the "don't annotate the job `@Component`" rule — is something Quartz itself requires. Quartz's own default model is `SimpleJobFactory` plus a public no-arg constructor (3.2); that's the whole contract from Quartz's point of view. Everything from 3.5 onward is this guide's chosen way of bridging that plain-Java model to Spring's constructor-injection convention — a deliberate, opinionated integration choice, not a rule Quartz hands you.

### 3.8 Writing the factory isn't enough — it also has to be wired in

This is the step almost everyone misses, and it's the one place Spring Boot's autoconfiguration behaves in a way that's genuinely easy to be misled by.

Recall from 3.0 that Spring Boot's autoconfiguration auto-detects certain bean types for you. For Quartz specifically, this is real and documented: **every `JobDetail` bean and every `Trigger` bean in your `ApplicationContext` gets automatically picked up and registered with the scheduler.** You never have to call `scheduler.scheduleJob(...)` yourself in a Spring Boot app — Spring Boot's autoconfiguration does it, by collecting every bean of those two types.

**`JobFactory` is a different story.** Checked directly against the source of Spring Boot's `QuartzAutoConfiguration` class:

```java
@Bean
@ConditionalOnMissingBean
public SchedulerFactoryBean quartzScheduler(QuartzProperties properties,
        ObjectProvider<SchedulerFactoryBeanCustomizer> customizers,
        ObjectProvider<JobDetail> jobDetails, Map<String, Calendar> calendars,
        ObjectProvider<Trigger> triggers, ApplicationContext applicationContext) {
    SchedulerFactoryBean schedulerFactoryBean = new SchedulerFactoryBean();
    SpringBeanJobFactory jobFactory = new SpringBeanJobFactory();
    jobFactory.setApplicationContext(applicationContext);
    schedulerFactoryBean.setJobFactory(jobFactory);
    // ...
}
```

A couple of things worth unpacking here for anyone less familiar with reading Spring source:

- `@ConditionalOnMissingBean` on this method means "only run this whole method — i.e., only create Spring Boot's default `SchedulerFactoryBean` — if the application hasn't already defined its own `SchedulerFactoryBean` bean." This is the general escape hatch mentioned in 3.0.
- `ObjectProvider<JobDetail> jobDetails` and `ObjectProvider<Trigger> triggers` are how the auto-detection from earlier in this section actually works, mechanically: Spring hands this method a lazy collection of every `JobDetail`/`Trigger` bean that exists anywhere in the application, and the rest of the method (not shown above) loops over them and registers each one.
- **There is no equivalent `ObjectProvider<JobFactory>` parameter.** `JobFactory` is not on the auto-detected list. Instead, this method builds its own plain `SpringBeanJobFactory` right there, inline, and calls `schedulerFactoryBean.setJobFactory(jobFactory)` on it — **unconditionally, every single time**, before your own beans (including a `JobFactory` bean you may have written) ever get a say.

The practical consequence: declaring `AutowiringSpringBeanJobFactory` as a `@Component`, by itself, accomplishes **nothing**. It becomes a perfectly valid bean, sitting in the `ApplicationContext` — and Spring Boot's `quartzScheduler()` method never looks at it, never asks the `ApplicationContext` for it, and installs its own separate plain `SpringBeanJobFactory` instead, which (per 3.4) can't handle `OrderExportJob`'s constructor injection at all.

**The fix is a `SchedulerFactoryBeanCustomizer`.** This is a callback interface Spring Boot's Quartz autoconfiguration specifically provides for exactly this kind of override — notice the `ObjectProvider<SchedulerFactoryBeanCustomizer> customizers` parameter in the source above. Every bean of this type gets called, in turn, with the already-built `SchedulerFactoryBean`, *after* Spring Boot's own defaults (including the plain `JobFactory`) have already been set on it:

```java
@Bean
public SchedulerFactoryBeanCustomizer jobFactoryCustomizer(AutowiringSpringBeanJobFactory jobFactory) {
    return schedulerFactoryBean -> schedulerFactoryBean.setJobFactory(jobFactory);
}
```

Note the parameter: `AutowiringSpringBeanJobFactory jobFactory`. Because that class is annotated `@Component` (it's the *factory* that should be a Spring-managed singleton — a genuinely different situation from the job class in 3.6, since there's exactly one factory instance, reused deliberately across every job type), it's a bean — so this `@Bean` method can simply ask for it as a parameter, and Spring's dependency injection supplies it, exactly as described in 3.0. The lambda passed to `SchedulerFactoryBeanCustomizer` then overwrites whatever `JobFactory` Spring Boot had already installed, replacing it with this custom one.

### 3.9 The complete picture, start to finish

```
Application starts up
        │
        ▼
Spring builds the ApplicationContext, registers all @Component/@Service beans
        │  (including OrderExportService and AutowiringSpringBeanJobFactory —
        │   but NOT OrderExportJob, which is deliberately not a bean, per 3.6)
        ▼
Spring Boot's quartzScheduler() bean method runs
        │
        ▼
Builds a plain SpringBeanJobFactory, calls setJobFactory() — unconditionally
        │
        ▼
Every SchedulerFactoryBeanCustomizer bean runs (order not guaranteed)
        │
        ▼
jobFactoryCustomizer overrides the JobFactory with AutowiringSpringBeanJobFactory
        │
        ▼
   Scheduler starts — using YOUR factory from this point on
        │
        ▼
Some time later, a trigger fires
        │
        ▼
Factory's createJobInstance() runs: beanFactory.createBean(OrderExportJob.class)
        │
        ▼
Spring resolves the constructor, autowires orderExportService from the context,
constructs a BRAND-NEW OrderExportJob instance
        │
        ▼
   execute() runs on this new instance
        │
        ▼
   Instance is discarded — the next firing repeats this from "trigger fires"
```

### 3.10 Rule of thumb

If any of your `Job` classes take constructor-injected dependencies — which almost all real ones will, especially with Lombok's `@RequiredArgsConstructor` generating that constructor for you:

1. **Do not annotate the job class itself with `@Component`** (3.6) — it doesn't need to be a bean, and marking it one just creates an unused duplicate instance.
2. **Do register the job's dependencies as beans normally** (`@Component`/`@Service` on `OrderExportService`, etc.) — `createBean(Class)` resolves the job's constructor arguments from the `ApplicationContext`, so those need to actually be there.
3. **Do wire `AutowiringSpringBeanJobFactory` in via a `SchedulerFactoryBeanCustomizer`** (3.8) — Spring Boot's default `SpringBeanJobFactory` never does this for you, regardless of how the job class or its dependencies are annotated.

### 3.11 What to use, depending on the job

| Situation | What to do |
|---|---|
| Job has a no-arg constructor, no dependencies at all | Default `SimpleJobFactory` works fine — no action needed |
| Job reads scheduling parameters through `JobDataMap`/trigger-data-matched setter properties (not `@Autowired`), and has a no-arg constructor | Default `SpringBeanJobFactory` works for this specific case — it populates setter properties whose names match job/trigger data keys (3.4). **This is not the same thing as Spring dependency injection**: it doesn't process `@Autowired` at all, on fields or setters — it's plain JavaBean-style property population driven by `JobDataMap` key names, unrelated to Spring's DI annotations |
| Job needs actual Spring beans injected — via `@Autowired` fields/setters or constructor injection | `AutowiringSpringBeanJobFactory` from 3.6, wired via `SchedulerFactoryBeanCustomizer` — job class itself stays a plain, non-`@Component` class. This is the only row of this table where `@Autowired` actually does anything |

### 3.12 Common failure modes

| Symptom | Cause | Fix |
|---|---|---|
| `NoSuchMethodException` on the job class, but only the first time its trigger fires — the app itself starts fine | Job has no no-arg constructor, and the scheduler is still using Spring Boot's default `SpringBeanJobFactory` | Wire `AutowiringSpringBeanJobFactory` (3.6) via a `SchedulerFactoryBeanCustomizer` (3.8) |
| Job executes without error, but its injected dependencies are `null` inside `execute()` | Plain `SpringBeanJobFactory` instantiated the job via its no-arg constructor and only populated setter properties matching job/trigger data keys — it never performs full dependency injection | Use the `createBean(Class)`-based factory from 3.6 instead |
| A custom `JobFactory` bean exists in the app, but it never seems to get called | No `SchedulerFactoryBeanCustomizer` registered — Spring Boot's own default factory is still silently in charge | Add a `SchedulerFactoryBeanCustomizer` bean that calls `setJobFactory(...)` with the custom factory |
| `UnsatisfiedDependencyException` when a trigger fires | The job class's constructor needs a type that isn't registered as a bean anywhere | Make sure every constructor parameter on the job class is itself a `@Component`/`@Service`/`@Bean` |
| Mutable state on a job class behaves unexpectedly across executions — values from one run bleed into another | The `getBean(jobClass)`-style factory from 3.5 is in use, making the job a de facto singleton | Switch to the `createBean(Class)` factory from 3.6, which creates a fresh instance every firing |
| Everything works locally in tests but fails in a live deployment on first fire | Tests may be constructing the job directly (e.g. `new OrderExportJob(mockService)`) rather than going through the real scheduler and factory | Add at least one integration test that lets a real trigger fire through the real, fully-wired scheduler (Part 11) |

## Part 4 — Data Flow: JobDataMap

### 4.1 Job data vs trigger data

Both `JobDetail` and `Trigger` carry their own `JobDataMap` — a `Map<String, Object>`-like structure for passing parameters into `execute()`. They're merged at execution time (trigger data takes precedence on key collisions), and accessed like this:

```java
public void execute(JobExecutionContext context) {
    JobDataMap jobData = context.getJobDetail().getJobDataMap();
    JobDataMap triggerData = context.getTrigger().getJobDataMap();
    String region = jobData.getString("region");
}
```

### 4.2 `getMergedJobDataMap()` vs separate maps

Quartz provides three ways to access job data:

| Method | What it returns | Use case |
|---|---|---|
| `context.getMergedJobDataMap()` | JobDetail + Trigger data combined | Most common — access everything in one map |
| `context.getJobDetail().getJobDataMap()` | Only JobDetail data | Need only job-level data |
| `context.getTrigger().getJobDataMap()` | Only Trigger data | Need only trigger-level data |

**Precedence rule:** When the same key exists in both maps, `getMergedJobDataMap()` returns the trigger's value.

```java
// JobDetail has: owner="admin@company.com"
// Trigger has:    owner="system@company.com"
// Merged returns: owner="system@company.com" (trigger wins)
```

### 4.3 When to use each

**JobDetail data** — shared by every trigger firing that `JobDetail`:
- Order region, file format, email recipient
- Configuration that doesn't change per trigger

```java
JobDetail job = JobBuilder.newJob(OrderExportJob.class)
    .withIdentity("exportJob", "order-export")
    .usingJobData("region", "DAILY")      // ← JobDetail data
    .usingJobData("owner", "admin@company.com")
    .build();
```

**Trigger data** — specific to that one trigger:
- Execution window, run ID, user who triggered it
- Unique values for each trigger pointing to the same job

```java
Trigger trigger1 = TriggerBuilder.newTrigger()
    .withIdentity("trigger1", "order-export")
    .usingJobData("executionId", "RUN-001")   // ← Trigger data
    .usingJobData("window", "MORNING")
    .build();

Trigger trigger2 = TriggerBuilder.newTrigger()
    .withIdentity("trigger2", "order-export")
    .usingJobData("executionId", "RUN-002")   // ← Different trigger data
    .usingJobData("window", "EVENING")
    .build();

// Same JobDetail, different triggers each with their own data
scheduler.scheduleJob(job, trigger1);
scheduler.scheduleJob(job, trigger2);
```

### 4.4 Recommended practice

For most cases, **use `getMergedJobDataMap()`** — it's simpler and gives you everything in one place. Only use separate maps when you need to distinguish which data source a value came from.

### 4.5 `useProperties` — the string-only constraint

By default, `JobDataMap` accepts any `Object`. But if you configure Quartz with:

```
org.quartz.jobStore.useProperties = true
```

...every value in every `JobDataMap` **must be a `String`**. This is a JDBC-JobStore-specific setting: when job data is persisted to a database (see Part 5), Quartz needs to serialize it somehow. `useProperties=true` stores it as flat string key-value pairs instead of Java serialization — which is far more robust across app redeploys (no `serialVersionUID` mismatches breaking a persisted trigger) and human-readable in the database. The tradeoff is exactly the constraint above: no storing a `LocalDateTime` or an `Instant` directly in job data — encode it as a string and parse it back out in `execute()`.

## Part 5 — Persistence and the JDBC JobStore

### 5.1 Why persistence matters

By default, Quartz keeps everything — jobs, triggers, schedule state — in memory (`RAMJobStore`). That's fine for a toy app; it's unacceptable for anything real, because **a process restart loses every scheduled job**. The `JDBCJobStore` persists all of it to a relational database, so scheduling state survives restarts and (critically) can be shared across multiple application instances — see Part 6.

### 5.2 Enabling it

```properties
spring.quartz.job-store-type=jdbc
spring.quartz.jdbc.initialize-schema=never
# you control schema migration, e.g. via Flyway/Liquibase
spring.quartz.properties.org.quartz.jobStore.tablePrefix=QRTZ_
```

**`initialize-schema` options:**

| Value | Behavior |
|---|---|
| `never` | You manage schema manually (Flyway/Liquibase) — recommended for production |
| `always` | Drops existing tables and recreates on every startup — **never use in production** |
| `embedded` | Only for embedded databases (H2/HSQL) — creates on startup if tables don't exist |

**Important:** For SQL Server, you must specify the delegate class:

```properties
spring.quartz.properties.org.quartz.jobStore.driverDelegateClass=org.quartz.impl.jdbcjobstore.MSSQLDelegate
```

Without this, don't expect the same "table doesn't exist" style of error — a missing or wrong delegate instead tends to surface as SQL syntax/dialect errors (Quartz's generic SQL doesn't match SQL Server's specific locking hints and pagination syntax), often on the very lock-acquisition queries clustering depends on (6.2). That's a distinct problem from "the tables aren't there at all" — see 5.6 for how to tell the two apart when something under `QRTZ_LOCKS` starts failing.

### 5.3 The schema

Quartz ships SQL scripts (`tables_*.sql`, one per database vendor) defining a substantial schema — `QRTZ_JOB_DETAILS`, `QRTZ_TRIGGERS`, `QRTZ_CRON_TRIGGERS`, `QRTZ_SIMPLE_TRIGGERS`, `QRTZ_FIRED_TRIGGERS`, `QRTZ_LOCKS`, and more. In any application already managing its own schema migrations, run these once through your own migration tool rather than letting Quartz auto-initialize — `initialize-schema=never` above is exactly that choice.

**Never hand-edit rows in these tables directly** — no `UPDATE QRTZ_TRIGGERS SET ...`, no manually deleting a row to "cancel" a job. Quartz's own tooling is explicit that this table structure is an internal implementation detail, not a stable data API: the encoding of trigger state, fired-trigger bookkeeping, and lock rows (5.6/6.2) all depend on invariants Quartz's own code maintains internally, and direct SQL against them can corrupt scheduler state or cause jobs to silently stop firing or appear to vanish. Keep the two concerns cleanly separated: your migration tool (Flyway/Liquibase) owns the *schema structure* — creating and upgrading these tables — while the `Scheduler` API (Part 9) is the only supported way to change *scheduling data* within them.

### 5.4 A dedicated DataSource for Quartz

A pattern worth knowing even before you need it: giving Quartz's `JDBCJobStore` its **own connection pool**, separate from the application's primary `DataSource`:

```java
@Configuration
public class QuartzDataSourceConfig {
    
    @Bean
    @QuartzDataSource
    @ConfigurationProperties("spring.datasource.quartz")
    public DataSource quartzDataSource() {
        return DataSourceBuilder.create().build();
    }
}
```

```properties
spring.datasource.quartz.url=jdbc:sqlserver://localhost:1433;databaseName=QuartzDB
spring.datasource.quartz.username=sa
spring.datasource.quartz.password=YourPassword
# Example value only — size based on measured Quartz concurrency and DB load, not this number
spring.datasource.quartz.hikari.maximum-pool-size=10
```

The `@QuartzDataSource` qualifier tells Spring Boot's Quartz autoconfiguration to use *this* pool instead of the primary one. Why bother? Quartz's clustered lock acquisition (Part 6) involves frequent short-lived polling queries competing for connections. Under load, if Quartz shares a pool with application traffic, the two can starve each other — a burst of order-export queries can delay Quartz's own lock check-ins (risking missed fires), or vice versa. A separate, appropriately-sized pool keeps the two workloads from ever fighting over the same limited connections.

**Sizing this pool:** don't reach for a fixed number like "5-10 connections" — I can't point you to an authoritative constant that fits every deployment, and neither can anyone else, because it genuinely depends on your `org.quartz.threadPool.threadCount` (Part 8), how often your application calls the `Scheduler` API directly (Part 9), and your cluster's node count. One nuance worth being careful about: `threadCount` isn't a direct stand-in for how many connections you need — a job can be executing for minutes at a time without holding a JDBC connection for that whole duration, so don't just copy the thread count into the pool size expecting a 1:1 relationship. What's true directionally is that the pool needs enough capacity for Quartz's own database operations (lock polling, 6.2), scheduler-API activity, and whatever connection usage your actual job logic and business transactions add on top — not a number derived from `threadCount` alone. Start with a deliberately modest pool, watch for connection-wait metrics, pool utilization, and timeouts under real traffic, and size up from that evidence rather than a formula or a number copied from a tutorial.

### 5.5 The redeploy gotcha nobody expects: `overwrite-existing-jobs`

Part 2.3 covered one redeploy surprise: a `JobDetail` with `storeDurably(false)` can disappear entirely if it briefly has no triggers. There's a second, opposite-feeling surprise that's arguably more common, and it's specific to the JDBC job store.

Once a `JobDetail` or `Trigger` has been persisted to the database, **Spring Boot will not overwrite it on a subsequent deploy by default.** Concretely: you change a cron expression in your Java code, or rename a job class, or add a new job data key — redeploy — and nothing happens. The scheduler keeps firing the *old* definition, because as far as it's concerned, a `JobDetail`/`Trigger` with that identity already exists in `QRTZ_JOB_DETAILS`/`QRTZ_TRIGGERS`, and by default it leaves existing persisted definitions alone rather than silently replacing them with whatever the code says today.

This is deliberate, not a bug: it protects against accidentally clobbering a schedule that was modified at runtime (e.g. paused, or rescheduled via the API in Part 8) by a routine code deploy. But it means **code changes to a job's schedule silently don't apply** unless you opt in:

```properties
spring.quartz.overwrite-existing-jobs=true
```

With this set, Spring Boot's autoconfiguration will overwrite a persisted `JobDetail`/`Trigger` with the one currently defined in your beans on every startup. Whether you actually want that is a real architectural decision, not a safe default — it comes down to who owns the schedule:

- **Code is the source of truth** (a typical CI/CD pipeline, where schedules are defined in version control and deploys should always reflect what's in the repo) — `overwrite-existing-jobs=true` is what you want, since a deploy should always make the database match the code.
- **The database/runtime is the source of truth** (schedules are administered at runtime — an ops team pauses a trigger, or an admin UI lets users adjust their own schedule via the dynamic scheduling API in Part 9) — `overwrite-existing-jobs=true` is actively dangerous here: the next routine deploy would silently undo whatever was changed at runtime, with no warning that it happened.

Decide explicitly which model your system follows before setting this property either way — don't enable it reflexively just because "code should win" sounds obviously correct in the abstract.

### 5.6 Common pitfalls

| Issue | Cause | Fix |
|---|---|---|
| `Invalid object name 'QRTZ_LOCKS'` | Tables don't exist or wrong `tablePrefix` | Run schema scripts or set `initialize-schema=always` (dev only) |
| `LockException` with SQL Server | Missing `MSSQLDelegate` | Add `driverDelegateClass=org.quartz.impl.jdbcjobstore.MSSQLDelegate` |
| `JobDataMap` fails to deserialize after a deployment | `useProperties=false` (Java serialization) with a value whose class changed shape between the deploy that stored it and the deploy reading it back — Java serialization inherently isn't guaranteed compatible across arbitrary class changes | Prefer `useProperties=true` with `String` values, which sidesteps class-compatibility entirely; if staying with `useProperties=false`, keep stored classes' shape stable across deploys |
| Connection pool exhaustion | Shared pool with application | Use separate `@QuartzDataSource` |
| Changed cron expression / job class has no effect after redeploy | Persisted `JobDetail`/`Trigger` in the JDBC store is left alone by default | Set `spring.quartz.overwrite-existing-jobs=true` |

## Part 6 — Clustering

### 6.1 The problem clustering solves

Run two instances of the same application, both with Quartz configured against the same JDBC job store, and — without clustering support — the outcome is worse than just "both instances fire the same trigger." Checked directly against Quartz's own tutorial documentation, its guidance here is blunt: never run a non-clustered scheduler instance against the same set of tables that another instance is running against. Quartz's own words are that doing so "may cause serious data corruption" and "will definitely experience erratic behavior" — not merely duplicate firings, but genuinely inconsistent scheduler state: jobs that appear to vanish, jobs that silently stop firing, deadlocks. Duplicate firing (your "export today's orders" job running twice, sending duplicate files to the warehouse) is one *visible symptom* of this misconfiguration, not the full extent of the risk. A shared JDBC job store with more than one scheduler instance pointed at it is only a supported configuration once clustering is actually turned on for all of them (6.2) — running multiple *non-clustered* instances against shared tables isn't a lesser version of clustering, it's an unsupported configuration entirely.

### 6.2 How Quartz clustering actually works

Enable it with:

```properties
spring.quartz.job-store-type=jdbc
spring.quartz.jdbc.initialize-schema=never
spring.quartz.properties.org.quartz.scheduler.instanceId=AUTO
spring.quartz.properties.org.quartz.scheduler.instanceName=MyClusteredScheduler
spring.quartz.properties.org.quartz.jobStore.isClustered=true
# Optional, default 15000ms
spring.quartz.properties.org.quartz.jobStore.clusterCheckinInterval=20000
spring.quartz.properties.org.quartz.jobStore.useProperties=true
spring.quartz.properties.org.quartz.jobStore.tablePrefix=QRTZ_
# SQL Server shown here as an example — use the delegate matching your actual
# database (5.2); omit this line entirely for databases Quartz's generic
# delegate already handles (PostgreSQL, MySQL, etc.)
spring.quartz.properties.org.quartz.jobStore.driverDelegateClass=org.quartz.impl.jdbcjobstore.MSSQLDelegate
spring.quartz.properties.org.quartz.threadPool.threadCount=10
spring.quartz.properties.org.quartz.threadPool.threadPriority=5
```

**`instanceId` options:**

| Value | Behavior |
|---|---|
| `AUTO` | Quartz generates a unique ID (hostname + timestamp) — **recommended** |
| `NON_CLUSTERED` | Single instance (default) |
| Custom value | Use only for advanced setups |

**`clusterCheckinInterval`** — How often each node checks in with the database. Default is 15000ms (15 seconds). There's no universally "right" value — it's a direct tradeoff: lower means faster detection of a failed node, at the cost of more constant database traffic across the cluster; higher means less database load, at the cost of a longer window before a dead node's abandoned work gets noticed and freed up. Start with the default and tune it based on how quickly you actually need failure detection to happen versus how much steady-state database overhead you're willing to accept — not toward a specific number picked in the abstract.

Every clustered node polls the shared database on an interval. When a trigger's fire time arrives, Quartz coordinates which node gets to claim it using transactional database state changes and database-backed locking — the exact SQL and locking mechanics depend on which `JobStore` and database delegate you're running, so treat "how" as an implementation detail rather than a fixed guarantee to build tooling around. Whatever the precise mechanism, the outcome is the same: exactly one node claims a given firing, fires the trigger, and releases its claim; every other node sees it as already taken and moves on. This is why the dedicated `spring.datasource.quartz` connection pool matters (5.4) — this acquisition traffic happens constantly, on every node, all the time the scheduler is running.

**The lock table (`QRTZ_LOCKS`) — corrected:** it's tempting to assume this table has one row per job, per trigger, or per trigger group, since that would map neatly onto "only one node fires a given trigger." That's not how it works. Checked directly against Quartz's cluster locking implementation (`StdRowLockSemaphore`), `QRTZ_LOCKS` holds a small, fixed set of **named** lock resources, completely independent of how many jobs/triggers/groups exist in your schedule — the core correction here is "not one lock per trigger," not a specific count. The current implementation uses two: `TRIGGER_ACCESS` (held while claiming triggers to fire — this is the cluster's actual serialization point for scheduling) and `STATE_ACCESS` (held during cluster check-in and failure-recovery bookkeeping); older Quartz versions and schemas have included additional named locks (`JOB_ACCESS`, `CALENDAR_ACCESS`, `MISFIRE_ACCESS`), and the exact set is implementation- and version-dependent rather than a fixed guarantee to build tooling around. Either way, a schedule with 5 triggers and one with 5,000 triggers coordinate through the same small, fixed set of lock rows — the table doesn't grow with your schedule size.

**Quartz does call this "load balancing" — but it's worth being precise about what kind.** Checked directly against Quartz's own clustering documentation, it explicitly describes clustering as providing failover *and* load balancing, stating that "load-balancing occurs automatically, with each node of the cluster firing jobs as quickly as it can." So it's not accurate to say clustering doesn't balance load at all — it does, in the sense that work does get spread across nodes rather than piling onto one. What it *isn't* is workload-aware:

```
                Shared DB
             ┌─────────────┐
             │ JDBC Store  │
             └──────┬──────┘
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
       Node A    Node B    Node C
       Quartz    Quartz    Quartz
```

Whichever node happens to win the lock race for a given firing runs it. Quartz itself describes the resulting distribution as "more or less random" for a busy scheduler with many triggers, and notes it can favor whichever node happens to be polling fastest for a lightly-loaded one. There's no round-robin, and critically, no awareness of CPU load, memory pressure, queue depth, or how long a given job typically takes — nothing resembling an HTTP load balancer's workload-aware routing. Don't build capacity planning around an assumption of *even, workload-aware* distribution — the balancing Quartz does is real, but it's closer to "random, and fast" than "smart."

### 6.3 Crash recovery in a cluster

**How failure detection works:**

1. Each node updates `QRTZ_SCHEDULER_STATE` with its `LAST_CHECKIN_TIME` every `clusterCheckinInterval`
2. If a node fails, its `LAST_CHECKIN_TIME` stops updating
3. Other nodes detect the stale record (roughly on the order of a few checkin intervals — the exact multiplier is an internal implementation detail worth checking against your specific Quartz version if the precise timing matters to you, rather than treating any single number here as guaranteed)
4. The `QRTZ_FIRED_TRIGGERS` records owned by the dead node are released
5. Triggers waiting on those firings are re-acquired by surviving nodes

If a node dies mid-execution of a job, what happens next depends entirely on `requestRecovery` (2.3). With `requestRecovery(true)`, another node in the cluster detects the abandoned "fired trigger" record and re-fires the job right away — your `execute()` method can tell this apart from a normal firing by checking `context.isRecovering()`, which returns `true` specifically on a recovered execution. **Without `requestRecovery(true)`, checked directly against Quartz's own clustering documentation, the job is not stuck or abandoned forever** — it's simply freed up and fires again normally at its next regularly scheduled time, the same as if nothing had happened. The practical difference `requestRecovery` actually controls is *timing*: `true` gets an interrupted execution redone immediately, on another node, without waiting for the next scheduled occurrence; `false` means whatever that interrupted execution was doing waits until the trigger's normal schedule brings it around again — which could be seconds away or a day away, depending on the schedule. Pick `true` for work where an immediate redo genuinely matters more than waiting for the next natural firing; leave it `false` where "it'll just run again next time" is an acceptable outcome.

**Recovery is not the same thing as retry, and it's worth keeping the two mentally separate:**

| | Trigger | Mechanism |
|---|---|---|
| **Retry** | Your job's own logic decided a business operation failed | Application-level: you write the retry loop yourself |
| **Recovery** | A node crashed mid-execution, abandoning the job entirely | Quartz-level: another node detects the abandoned firing and re-fires it, if `requestRecovery(true)` |
| **Misfire** (2.2) | A trigger's scheduled fire time passed without firing at all | Quartz-level: the misfire instruction decides whether to fire late or skip |

All three can result in a job's `execute()` running again for what's logically "the same" scheduled work — which is exactly why idempotency (covered in Part 10) matters regardless of which of the three you're dealing with.

Any job's `JobDataMap` has to be persistable to run under `JDBCJobStore` at all — this applies uniformly, whether or not `requestRecovery` is set: either `useProperties=true` (string-only) or every value being `Serializable` for Java-serialized storage.

### 6.4 Common pitfalls

| Symptom | Probable cause | Fix |
|---|---|---|
| Multiple nodes fire same trigger | `isClustered=false` | Set `isClustered=true` on all nodes |
| Node appears offline but is running | `clusterCheckinInterval` set too high relative to how quickly you need failure detected | Lower it, weighing against the added database check-in traffic (6.2) — there's no universal number, tune from the default |
| Job doesn't execute again immediately after a node crashes mid-execution | `requestRecovery(false)` — this is Quartz behaving exactly per configuration, not a failure; per 6.3, the job is freed for its next regularly scheduled firing instead of an immediate re-run | If an immediate redo after a crash genuinely matters more than waiting for the next natural firing, set `requestRecovery(true)` on the `JobDetail` |
| `serialVersionUID` errors in cluster | Using Java serialization with rolling deployment | Set `useProperties=true` |
| Lock acquisition timeouts | Not enough connections in pool | Increase pool size or use `@QuartzDataSource` |

## Part 7 — Concurrency Control

### 7.1 `@DisallowConcurrentExecution`

By default, if a trigger fires again while the *previous* firing of the same `JobDetail` is still running, Quartz happily starts a second concurrent execution. For most stateful or resource-bound jobs, that's dangerous. Annotate the `Job` class:

```java
@DisallowConcurrentExecution
public class OrderExportJob implements Job {
    // ...
}
```

Now Quartz will block a new firing of this `JobDetail` from starting until the current one finishes.

**Under the hood:** this is the `BLOCKED` trigger state from Part 2.5 in action. When you annotate a job with `@DisallowConcurrentExecution`, Quartz tracks that as a flag on the `JobDetail`. If a trigger's fire time arrives while another execution of the same `JobDetail` is still `EXECUTING`, that trigger doesn't fire, get skipped, or get treated as a misfire — it transitions to `BLOCKED` and sits there, still owed its firing, until the running execution finishes and the `JobDetail` frees up. At that point it becomes eligible again. Nothing about the missed window is lost the way a genuine misfire (2.2) can lose one — it's simply deferred until the job is free to run it.

**Granularity:** This is enforced **per `JobDetail`**, not per class — two different `JobDetail`s both backed by the same `Job` class can still run concurrently with each other; it's firings of the *same* `JobDetail` that get serialized.

```java
@DisallowConcurrentExecution
public class OrderExportJob implements Job { ... }

// Two different JobDetails, both using OrderExportJob
JobDetail job1 = JobBuilder.newJob(OrderExportJob.class)
    .withIdentity("job1", "group1").build();
JobDetail job2 = JobBuilder.newJob(OrderExportJob.class)
    .withIdentity("job2", "group1").build();

// job1 and job2 can run concurrently with each other
// Multiple firings of job1 are serialized
```

### 7.2 `@PersistJobDataAfterExecution`

A related annotation: if your job mutates its own `JobDataMap` during `execute()` (e.g. incrementing a counter) and you want that change persisted back to the job store, add `@PersistJobDataAfterExecution`.

**Under the hood:** When you annotate a job with `@PersistJobDataAfterExecution`, Quartz updates the `JOB_DATA` column in `QRTZ_JOB_DETAILS` after each execution. This means any changes made to the `JobDataMap` within `execute()` are saved to the database.

```java
@PersistJobDataAfterExecution
public class CounterJob implements Job {
    @Override
    public void execute(JobExecutionContext context) {
        JobDataMap data = context.getJobDetail().getJobDataMap();
        int count = data.getInt("count");
        data.put("count", count + 1);  // Persisted after execution
        System.out.println("Count: " + count);
    }
}
```

### 7.3 The combination: both annotations together

`@PersistJobDataAfterExecution` is commonly paired with `@DisallowConcurrentExecution`, since mutating shared job data safely generally also requires that no second execution is running concurrently.

This combination is common enough that Quartz's own documentation explicitly recommends it: **if you annotate a job with `@PersistJobDataAfterExecution`, you should also annotate it with `@DisallowConcurrentExecution`** to avoid race conditions. To be precise about what's actually happening here — Quartz doesn't enforce or automate this pairing in any way; there's no validation that stops you from using one annotation without the other. It's advisory, not automatic: without `@DisallowConcurrentExecution`, two concurrent executions of the same `JobDetail` could both read the same starting `JobDataMap`, mutate it independently, and race to persist their own version — silently losing whichever update saved first. The annotation pairing is on you to apply consistently.

```java
@DisallowConcurrentExecution
@PersistJobDataAfterExecution
public class CounterJob implements Job {
    @Override
    public void execute(JobExecutionContext context) throws JobExecutionException {
        JobDataMap data = context.getJobDetail().getJobDataMap();
        int count = data.getInt("count");
        data.put("count", count + 1);
        System.out.println("Count: " + count);
    }
}
```

**This example demonstrates the mechanism, not a recommended persistence strategy.** `JobDataMap` is scheduling metadata, not a general-purpose application state store — it's a small, `String`-keyed map (Part 4.5) meant for parameters that shape how a job runs, not for business data your application actually cares about. For anything that matters — counts, statuses, business records — use your application's own database or domain model, where you get real querying, real transactions, and real durability guarantees that `JobDataMap` was never designed to provide.

### 7.4 Synchronous vs asynchronous job launches

Worth calling out because it's a real design decision, not just a Quartz mechanic.

**The problem:** If your `Job.execute()` kicks off further async work (e.g. launching a Spring Batch job, sending messages to a queue, or calling an async REST API) and returns immediately, Quartz considers the *trigger firing* complete the moment `execute()` returns — **not when the async work finishes.**

**Consequences:**
- `@DisallowConcurrentExecution` stops meaning "one at a time" for the actual underlying work — only for the thin synchronous wrapper, since as far as Quartz can tell, the job already finished
- Quartz has no visibility into the async work at all once `execute()` returns — no ability to report accurate completion status, no way to catch an eventual failure in it, nothing
- You can have multiple async executions running concurrently even with `@DisallowConcurrentExecution`, since each `execute()` call returns immediately and Quartz sees no overlap

**Example of what NOT to do:**
```java
@DisallowConcurrentExecution
public class OrderExportJob implements Job {
    private final OrderExportService service;
    
    @Override
    public void execute(JobExecutionContext context) {
        // ❌ BAD: Returns immediately, but real work continues in background
        service.exportOrdersAsync()  // CompletableFuture<Void>
            .thenRun(() -> log.info("Export completed"));
        // Quartz thinks the job is done!
    }
}
```

**Correct approach:**
```java
@DisallowConcurrentExecution
public class OrderExportJob implements Job {
    private final OrderExportService service;
    
    @Override
    public void execute(JobExecutionContext context) throws JobExecutionException {
        try {
            // ✅ GOOD: Block until the work is actually done
            service.exportOrdersSync();  // Blocks until complete
            // OR
            service.exportOrdersAsync().get(30, TimeUnit.SECONDS);  // Wait for completion
        } catch (Exception e) {
            throw new JobExecutionException("Order export failed", e);
        }
    }
}
```

If real completion matters for either concurrency control or misfire handling, `execute()` needs to block until the underlying work is actually done — even if the thing it launches offers an async API.

### 7.5 Common pitfalls

| Symptom | Probable cause | Fix |
|---|---|---|
| Jobs are running concurrently | Missing `@DisallowConcurrentExecution` | Add the annotation |
| Job data changes not persisted | Missing `@PersistJobDataAfterExecution` | Add the annotation |
| Corrupted job data | Using `@PersistJobDataAfterExecution` without `@DisallowConcurrentExecution` | Add `@DisallowConcurrentExecution` |
| Multiple jobs running despite `@DisallowConcurrentExecution` | Using async work inside `execute()` | Make `execute()` block until work completes |

## Part 8 — Putting It Together: A Realistic Config Shape

Tying the previous parts into one coherent shape (structurally close to a real clustered, JDBC-backed setup):

### 8.1 Complete configuration

```java
@Configuration
public class QuartzSchedulerConfig {

    @Bean
    public JobDetail exportJobDetail() {
        return JobBuilder.newJob(OrderExportJob.class)
                .withIdentity("dailyOrderExport", "order-export")
                .storeDurably(true)
                .requestRecovery(true)
                .build();
    }

    @Bean
    public Trigger exportTrigger(JobDetail exportJobDetail) {
        return TriggerBuilder.newTrigger()
                .forJob(exportJobDetail)
                .withIdentity("dailyOrderExport-trigger", "order-export")
                .withSchedule(CronScheduleBuilder.cronSchedule("0 0 6 * * ?")
                        .inTimeZone(TimeZone.getTimeZone("America/New_York"))
                        .withMisfireHandlingInstructionFireAndProceed())
                .build();
    }

    // JobFactory is REQUIRED here, not optional: OrderExportJob takes constructor-
    // injected dependencies. Spring Boot's default SpringBeanJobFactory can only call
    // a no-arg constructor (Part 3.4), and OrderExportJob is deliberately NOT annotated
    // @Component (Part 3.6) — it's built fresh on every firing by the factory below via
    // AutowireCapableBeanFactory.createBean(), not looked up as an existing singleton.
    // Without this customizer, the job builds and boots fine but throws an exception
    // the moment its trigger first fires.
    @Bean
    public SchedulerFactoryBeanCustomizer jobFactoryCustomizer(AutowiringSpringBeanJobFactory factory) {
        return bean -> bean.setJobFactory(factory);
    }
}
```

**Why the customizer pattern works:** Spring Boot's `QuartzAutoConfiguration` creates a `SchedulerFactoryBean` with `@ConditionalOnMissingBean`. This means:
- If you define your own `SchedulerFactoryBean`, Spring Boot uses yours
- If you don't, Spring Boot creates its default one

The `SchedulerFactoryBeanCustomizer` pattern is preferred over defining your own `SchedulerFactoryBean` because it preserves Spring Boot's defaults and only overrides what you need.

**Spring Boot auto-detection:**
- All `JobDetail` beans are auto-scheduled
- All `Trigger` beans are auto-scheduled
- You don't need to call `scheduler.scheduleJob()` manually

### 8.2 Complete application.properties configuration

```properties
# Quartz Configuration

# Scheduler Properties
```

### 8.3 Debugging checklist

| Symptom | Check | Fix |
|---|---|---|
| Job/trigger not firing at all | `JobDetail`/`Trigger` bean registration | Ensure beans exist and are auto-detected |
| Job/trigger not firing at all | Misfire instructions (Parts 1-2) | Set appropriate `withMisfireHandlingInstruction...` |
| Job throws on instantiation | `JobFactory` wiring (Part 3.8), or the job class was mistakenly annotated `@Component` (Part 3.6) | Wire `AutowiringSpringBeanJobFactory` via a `SchedulerFactoryBeanCustomizer`; leave the job class itself as a plain, non-`@Component` class |
| Same `JobDetail` executes concurrently with itself | Missing `@DisallowConcurrentExecution` (Part 7.1) | Add the annotation — note this only prevents *concurrent* overlap of one `JobDetail`; it doesn't prevent a job running twice for other reasons (see below) |
| Same logical work runs twice, but never concurrently | Misfire catch-up, cluster recovery, a manual `triggerJob()`, or an upstream duplicate (Part 10.1) | `@DisallowConcurrentExecution` won't help here — this is what idempotency (Part 10.2) is for |
| Same firing executes on more than one node | Clustering config (Part 6) | Verify `isClustered=true` and `instanceId=AUTO` on every node |
| A job class runs on two different schedules and that's unexpected | Two separate `JobDetail`s both built from the same `Job` class (Part 7.1) — this is legitimate, independent scheduling, not a bug | Confirm whether that's actually intended; if not, consolidate to one `JobDetail` |
| A `JobDetail` disappears once its last trigger is removed | `storeDurably(false)` (Part 2.3) — note this is specifically about a `JobDetail` reaching zero triggers, not "any redeploy" | Set `storeDurably(true)` if you plan to manage triggers on it independently over time |
| Schedule vanishes after redeploy, unrelated to triggers being removed | Using `RAMJobStore` | Switch to `JDBCJobStore` (`job-store-type=jdbc`) |
| Changed cron/job code has no effect after redeploy | Persisted definition in JDBC store isn't overwritten by default (Part 5.5) | Set `spring.quartz.overwrite-existing-jobs=true` |
| `JobDataMap` mutations during `execute()` aren't saved | Missing `@PersistJobDataAfterExecution` (Part 7.2) | Add the annotation if you actually need this — see Part 7.2's caveat about what `JobDataMap` is (and isn't) for |
| Serialization/type errors involving `JobDataMap` | `useProperties` controls *how* values are stored (string-only vs. Java serialization, Part 4.5) — it doesn't control *whether* the map persists at all | Set `useProperties=true` and ensure every value is a `String`, or ensure every value is genuinely `Serializable` if leaving it `false` |

### 8.4 Summary

Read as a checklist, this is also a decent debugging sequence when a Quartz-based scheduler misbehaves:

1. **Job/trigger not firing at all** → check `JobDetail`/`Trigger` bean registration and misfire instructions (Parts 1–2)
2. **Job throws on instantiation the first time it fires** → check `JobFactory` wiring (Part 3)
3. **Job executes more than once** → first determine whether the executions actually overlapped. If they overlapped, check `@DisallowConcurrentExecution` (Part 7.1). If they didn't overlap, `@DisallowConcurrentExecution` isn't the relevant control at all — investigate misfire catch-up, cluster recovery, a manual `triggerJob()`, or an upstream duplicate instead (Part 10), and make the underlying work idempotent regardless of which one it turns out to be
4. **A `JobDetail` disappears once its last trigger is removed** → check `storeDurably` (Part 2.3); if the schedule disappears on redeploy for a different reason entirely, check whether you're accidentally on `RAMJobStore` instead of `JDBCJobStore` (Part 5)
5. **`JobDataMap` mutations during `execute()` aren't saved** → check for `@PersistJobDataAfterExecution` (Part 7.2); for serialization/type errors involving `JobDataMap` specifically, check `useProperties` and the types being stored (Part 4.5) — `useProperties` controls *how* values are represented, not *whether* the map persists at all

### 8.5 Graceful shutdown in Spring Boot

Part 1.6 covered graceful shutdown for plain Quartz — a manual JVM shutdown hook calling `scheduler.shutdown(true)`. Once Spring Boot's autoconfiguration owns the `Scheduler` (as it has since Part 3), you don't write that hook yourself. `SchedulerFactoryBean` already participates in Spring's own application shutdown sequence, and the same "wait for in-flight jobs to finish" behavior is a property:

```properties
spring.quartz.wait-for-jobs-to-complete-on-shutdown=true
```

This defaults to `false` — meaning by default, Spring Boot shuts the scheduler down without waiting for currently-executing jobs, the same tradeoff `shutdown(false)` represents in Part 1.6. Set it to `true` for the same reason you'd choose `shutdown(true)` manually: if a job can't safely be interrupted mid-execution, you want the application to wait for it before the JVM exits (e.g. during a rolling deploy). Two related properties round this out:

| Property | Purpose | Default |
|---|---|---|
| `spring.quartz.wait-for-jobs-to-complete-on-shutdown` | Wait for running jobs before shutdown | `false` |
| `spring.quartz.auto-startup` | Whether the scheduler starts automatically at application startup | `true` |
| `spring.quartz.startup-delay` | Delay (as a duration, e.g. `10s`) before the scheduler starts firing triggers after startup — useful to let the rest of the application finish initializing first | `0s` |

If you find yourself writing a manual `Runtime.getRuntime().addShutdownHook(...)` in a Spring Boot application to control Quartz's shutdown, that's a sign the built-in property above is what you actually want instead — a hand-written hook alongside Spring's own lifecycle management is redundant at best, and can shut things down in an order you didn't intend at worst.

One more property worth knowing exists, given how much emphasis Part 10.5 places on Quartz's transaction boundary being separate from your own: if Quartz genuinely needs to use a different `PlatformTransactionManager` than your application's primary one, Spring Boot supports designating one specifically for Quartz via `@QuartzTransactionManager` — see "Where to go from here" for more.

## Part 9 — Dynamic Scheduling

Everything through Part 8 assumes jobs and triggers are defined once, as beans, at application startup — Spring Boot's autoconfiguration collects them and hands them to the scheduler before your application ever serves a request. That covers a lot of real systems. But plenty of others need schedules that change *while the application is running* — an admin panel that lets an operator pause a job, a per-customer schedule stored in a database and created on demand, a "run this right now" button. That's what the `Scheduler` interface's own API is for.

### 9.1 Getting hold of the `Scheduler`

In a Spring Boot app, the autoconfigured `Scheduler` is itself a bean — inject it like anything else:

```java
@Service
@RequiredArgsConstructor
public class ScheduleAdminService {
    private final Scheduler scheduler;
    // methods below use this directly
}
```

### 9.2 Creating and removing schedules at runtime

```java
// Schedule a new job + trigger
scheduler.scheduleJob(jobDetail, trigger);

// Add another trigger to an EXISTING JobDetail (this is exactly why storeDurably
// matters — Part 2.3 — a durable JobDetail can outlive having zero triggers,
// which is required for this kind of incremental, dynamic scheduling)
scheduler.scheduleJob(newTrigger);

// Replace a trigger's schedule entirely, keeping the same TriggerKey
scheduler.rescheduleJob(triggerKey, newTrigger);

// Remove one trigger, leaving the JobDetail (and any other triggers on it) alone
scheduler.unscheduleJob(triggerKey);

// Remove a JobDetail and every trigger attached to it
scheduler.deleteJob(jobKey);

// Check before you create, to avoid ObjectAlreadyExistsException
if (!scheduler.checkExists(jobKey)) {
    scheduler.scheduleJob(jobDetail, trigger);
}
```

`scheduleJob(jobDetail, trigger)` throws `ObjectAlreadyExistsException` if a `JobDetail` or `Trigger` with that identity already exists — which is exactly why `checkExists` matters for any code path that might run more than once (a retried admin action, a duplicate event). **`checkExists` is a convenience for normal, sequential administration — it is not a substitute for handling concurrent access.** It answers "does this exist right now," and by the time your next line of code acts on that answer, another caller could have changed things. Where more than one writer is genuinely possible (9.3), the `Scheduler` API's own exceptions (`ObjectAlreadyExistsException` and friends) remain the actual source of truth — code that can be called concurrently should be prepared to catch and handle them, not just check-then-act and assume the check still holds.

Which call to reach for depends on exactly what's changing:

| What changed | Use |
|---|---|
| Just the trigger's schedule (cron expression, interval) | `rescheduleJob(triggerKey, newTrigger)` — replaces the trigger without touching the `JobDetail` |
| The `JobDetail` itself (job class, job-level data) | `addJob(jobDetail, true)` — the `true` means "replace if it already exists," updating in place rather than requiring delete-then-recreate |
| Remove one trigger, keep the job | `unscheduleJob(triggerKey)` |
| Remove the job and everything attached to it | `deleteJob(jobKey)` |
| Run it once, right now, outside the schedule | `triggerJob(jobKey)` (9.5) |

Prefer the targeted call over delete-then-recreate where one applies — 9.3's example uses `deleteJob` + `scheduleJob` because it's replacing both the `JobDetail` and trigger together for simplicity, but if only the trigger's time is changing, `rescheduleJob` is the narrower, less disruptive operation.

### 9.3 A worked example: per-customer schedules from a database

This is the shape that comes up constantly in practice — "every customer can configure their own daily export time":

```java
@Service
@RequiredArgsConstructor
public class CustomerScheduleService {

    private final Scheduler scheduler;

    public void upsertSchedule(String customerId, LocalTime exportTime, String timezone) {
        JobKey jobKey = new JobKey("export-" + customerId, "customer-export");
        TriggerKey triggerKey = new TriggerKey("export-" + customerId + "-trigger", "customer-export");

        JobDetail jobDetail = JobBuilder.newJob(OrderExportJob.class)
                .withIdentity(jobKey)
                .usingJobData("customerId", customerId)
                .storeDurably(true)
                .requestRecovery(true)
                .build();

        Trigger trigger = TriggerBuilder.newTrigger()
                .withIdentity(triggerKey)
                .forJob(jobKey)
                .withSchedule(CronScheduleBuilder.dailyAtHourAndMinute(exportTime.getHour(), exportTime.getMinute())
                        .inTimeZone(TimeZone.getTimeZone(timezone))
                        .withMisfireHandlingInstructionFireAndProceed())
                .build();

        if (scheduler.checkExists(jobKey)) {
            scheduler.deleteJob(jobKey); // clears out the old JobDetail + trigger(s) together
        }
        scheduler.scheduleJob(jobDetail, trigger);
    }

    public void removeSchedule(String customerId) {
        scheduler.deleteJob(new JobKey("export-" + customerId, "customer-export"));
    }
}
```

Stable, deterministic `JobKey`/`TriggerKey` identity (derived from `customerId`, not a random UUID) is what makes this safe to call **sequentially** — `upsertSchedule` can run again for the same customer at any later time and correctly replace the old schedule rather than accumulating duplicates. This is also precisely the scenario from Part 5.5 where `spring.quartz.overwrite-existing-jobs` should almost certainly be **left off** — these schedules are managed at runtime through this service, not through static beans, so there's no "code redeploy" case where you'd want a deploy to silently clobber a customer's chosen time.

**This example assumes one writer at a time per customer, and it's worth being upfront about that.** The `checkExists` → `deleteJob` → `scheduleJob` sequence is a classic check-then-act: two concurrent calls to `upsertSchedule` for the *same* `customerId` (a double-submitted form, a retried request) can both pass `checkExists`, both call `deleteJob`, and then race on `scheduleJob` — one succeeding, one potentially hitting `ObjectAlreadyExistsException` or simply overwriting the other's intent depending on timing. For a genuinely concurrent-safe version, either serialize updates per customer (a lock keyed on `customerId`, or a queue), or reach for `rescheduleJob(triggerKey, newTrigger)` (9.2) when only the trigger's schedule is changing — it replaces a `Trigger` by key without the separate delete-then-recreate steps, which narrows, though doesn't by itself eliminate, the race window.

### 9.4 Pausing and resuming

For maintenance windows, incident response, or giving an operator a "stop this without deleting it" button:

```java
scheduler.pauseJob(jobKey);        // pause every trigger on this JobDetail
scheduler.resumeJob(jobKey);

scheduler.pauseTrigger(triggerKey); // pause just one trigger
scheduler.resumeTrigger(triggerKey);

scheduler.pauseAll();   // pause the entire scheduler — every job, every trigger
scheduler.resumeAll();
```

A paused trigger's fire times are **not** treated as misfires when you resume it (2.2) — Quartz knows the gap was intentional, not a failure to fire, and simply picks back up from its normal schedule rather than trying to "catch up" on everything it skipped while paused.

### 9.5 Running a job on demand, outside its schedule

```java
scheduler.triggerJob(jobKey);

// with extra data available to that one specific firing, via the trigger's JobDataMap
JobDataMap runNowData = new JobDataMap();
runNowData.put("triggeredBy", "admin-ui");
scheduler.triggerJob(jobKey, runNowData);
```

This fires the `JobDetail` immediately, once, without touching its regular schedule at all — exactly the mechanism behind an admin panel's "run now" button, and, as it happens, the cleanest way to integration-test a job (Part 11).

### 9.6 Common pitfalls

| Symptom | Cause | Fix |
|---|---|---|
| `ObjectAlreadyExistsException` on a retried or duplicate admin action | `scheduleJob(...)` doesn't overwrite by default | Check `scheduler.checkExists(jobKey)` first, or use `rescheduleJob`/delete-then-recreate for an intentional replace |
| Dynamically-created `JobDetail` disappears unexpectedly | `storeDurably(false)` and its only trigger was removed | Use `storeDurably(true)` for any `JobDetail` you plan to manage triggers on independently (Part 2.3) |
| A customer's runtime-configured schedule gets wiped out after a deploy | `spring.quartz.overwrite-existing-jobs=true` is set, and this schedule was never defined as a bean in the first place | Per Part 5.5 — decide explicitly whether code or the database owns this schedule; runtime-managed schedules like 9.3 want this property off |
| `triggerJob()` silently does nothing | `jobKey` doesn't match any registered `JobDetail` | Confirm with `scheduler.checkExists(jobKey)` before triggering |

## Part 10 — Idempotency, Retries, and JobExecutionException

### 10.1 The central assumption: your job *will* run more than once for the same logical work

This is arguably the single most important production habit in this whole guide, and it's worth stating as a rule rather than a scattered aside: **write every job assuming `execute()` can run more than once for what is logically the same unit of work.** Not as a remote edge case — as something that will genuinely happen, for several independent reasons already covered separately across this guide:

- A **misfire whose policy triggers a catch-up firing**, such as `FireAndProceed` (2.2) — the misfire itself is just a missed fire time; whether that results in an extra execution depends entirely on which misfire instruction the trigger was given
- A **crash recovery** (6.3) re-fires the job on another cluster node
- A `JobExecutionException` with `refireImmediately` set (10.3, below)
- An operator manually calling `triggerJob()` (9.5) for a window that already ran
- A duplicate business event arriving twice from an upstream system
- Simple human error — someone re-running a deploy, re-triggering an action

None of these are exotic. A job that assumes "I will run exactly once per logical unit of work" is a job that will eventually double-process something in production.

### 10.2 What idempotency actually looks like in a job

The fix is to make `execute()` safe to run twice — check whether the work already happened before doing it again:

```java
@Override
public void execute(JobExecutionContext context) {
    String batchId = buildBatchId(context); // deterministic — same window always produces the same ID

    if (orderExportService.alreadyProcessed(batchId)) {
        log.info("Batch {} already processed, skipping", batchId);
        return;
    }

    orderExportService.exportPendingOrders(batchId);
    orderExportService.markProcessed(batchId);
}
```

The load-bearing detail is `buildBatchId` being **deterministic** — the same reporting window has to produce the same ID every time it's computed, regardless of which node computes it or how many times. A random UUID generated fresh on each firing defeats the whole mechanism, since `alreadyProcessed` would never find a match. Deriving the ID from the window's own boundaries (e.g. `region + windowStartUtc + windowEndUtc`) is the usual approach.

**One honest caveat about the example above: it's check-then-act, not atomic.** `alreadyProcessed(batchId)` and `markProcessed(batchId)` are two separate calls with a gap between them — if two executions of the same batch genuinely overlap (say, a `@DisallowConcurrentExecution` gap gets bypassed some other way, or two independent trigger paths compute the same `batchId`), both could see `alreadyProcessed` return `false` before either has finished. `@DisallowConcurrentExecution` (Part 7.1) closes most of this gap for a single `JobDetail`, but the example as written still isn't safe against every possible concurrent caller — a cluster recovery re-fire racing a slow-to-complete original execution, for instance. For a genuinely atomic claim, push the check-and-claim into a single database operation rather than two application-level calls — e.g. an `INSERT` into a table with a `UNIQUE(batch_id)` constraint, where a duplicate-key failure *is* the "already processed" signal, or a small state machine (`PENDING` → `PROCESSING` → `COMPLETED`) with the transition itself guarded by the database. The version above is worth understanding first because it makes the *concept* clear; treat the atomic version as what you'd actually want to ship.

### 10.3 `JobExecutionException`'s full signature

Every failure-handling example so far has thrown `JobExecutionException` with just a message and cause. It has a richer constructor that tells Quartz what to do next, and it's worth actually knowing what it can do:

```java
public JobExecutionException(Throwable cause, boolean refireImmediately)
public JobExecutionException(String msg, Throwable cause, boolean refireImmediately)
```

And two setters available on any `JobExecutionException` instance, called before throwing it:

```java
JobExecutionException e = new JobExecutionException("Export failed, retrying", cause);
e.setRefireImmediately(true);   // ask Quartz to fire this job again right away
// or:
e.setUnscheduleFiringTrigger(true);  // stop firing THIS trigger going forward
// or:
e.setUnscheduleAllTriggers(true);    // stop firing EVERY trigger pointed at this JobDetail
throw e;
```

| Flag | Effect |
|---|---|
| `refireImmediately` | Quartz immediately refires the current job execution — not an ordinary new scheduled firing of the `JobDetail`, but a direct re-run of the one that just failed, bypassing the normal schedule entirely — a Quartz-native "retry right now" |
| `setUnscheduleFiringTrigger(true)` | The trigger that just fired is unscheduled — it won't fire again on its normal schedule |
| `setUnscheduleAllTriggers(true)` | Every trigger currently pointing at this `JobDetail` is unscheduled |

**In practice, prefer application-level retry logic (a `Retry` wrapper, a message queue's own redelivery, exponential backoff you control) over `refireImmediately` for anything beyond a handful of immediate attempts.** `refireImmediately` has no backoff, no attempt limit, and no distinction between "transient blip, try again in a second" and "this will fail identically forever" — a persistently-failing job with `refireImmediately` set can spin tight against your database or downstream systems. It exists and is worth knowing about, but the unschedule flags are the ones more often worth reaching for in practice — halting a trigger (or every trigger on a `JobDetail`) after a failure that isn't going to self-resolve is often exactly the right instinct, versus letting a broken schedule keep firing into the void every day until someone happens to notice.

### 10.4 Three distinct concepts that are easy to blur together

Across this guide, three separate mechanisms can all result in `execute()` running again for logically the same work. Part 6.3 already introduced recovery vs. retry; here's the complete picture with misfire included:

| Concept | What triggers it | Layer |
|---|---|---|
| **Misfire** (2.2) | A trigger's scheduled fire time passed without firing at all (scheduler was down, thread pool busy) | Quartz — governed by the trigger's misfire instruction |
| **Recovery** (6.3) | A cluster node crashed mid-execution, abandoning the job | Quartz — governed by `requestRecovery(true)` and cluster check-in |
| **Retry** | Your job's own logic decided a business operation failed and should be attempted again | Application — you write this yourself, at whatever granularity you choose |

Idempotency (10.2) is what makes all three safe simultaneously, without you needing to reason about which specific one caused a given re-execution.

### 10.5 A note on transactions: Quartz's and yours are not the same one

Worth being explicit about, since it's easy to assume a successful job execution implies your business operation is safely committed. It doesn't, automatically. Quartz's JDBC job store (`JobStoreTX`) manages its own database transactions — for bookkeeping like marking a trigger as fired, updating `QRTZ_FIRED_TRIGGERS`, and so on. Your job's business logic almost certainly has its own, entirely separate transaction (or none at all, if it's calling out to an external system).

A concrete failure shape: your job's database transaction commits successfully, but then sending a follow-up notification email throws and the job fails. The database write is real and permanent; the email never went out — and there is no way to "roll back" the successful database commit because a later step failed. Or the reverse: the export succeeds and an external API call is made, but *then* an exception is thrown before your own bookkeeping records the export as complete — the external side effect already happened and can't be undone by anything failing afterward.

This is precisely why 10.2's idempotency check matters even for jobs that "never fail" in normal operation — the failure mode isn't really about your job's logic being wrong, it's about partial completion across a boundary Quartz has no visibility into and no ability to coordinate for you.

## Part 11 — Testing Quartz Jobs

### 11.1 Test the business logic directly — don't go through Quartz at all

The most valuable Quartz-related test usually doesn't involve Quartz. `OrderExportJob.execute()` should be a thin wrapper (Part 3.6-3.7 already established why it should stay thin: it's rebuilt fresh on every firing, with no state of its own). Test the logic it delegates to directly:

```java
@Test
void exportsOnlyPendingOrders() {
    OrderExportService service = new OrderExportService(fakeOrderRepository);
    service.exportPendingOrders("2026-08-17");
    assertThat(fakeOrderRepository.exportedOrderIds()).containsExactly("order-1", "order-3");
}
```

No `JobExecutionContext`, no `Scheduler`, no `JobFactory` — none of it is relevant to whether the export logic itself is correct. Reserve `JobExecutionContext` mocking for the thin translation layer inside `execute()` itself, if it's complex enough to need its own test at all.

### 11.2 Integration-testing the schedule itself

For "does this actually get wired up and fire correctly," fire it on demand rather than waiting on a real schedule — `scheduler.triggerJob()` from Part 9.5 is the tool:

```java
@SpringBootTest
class OrderExportScheduleIntegrationTest {

    @Autowired
    private Scheduler scheduler;

    @Test
    void jobFiresAndExecutesSuccessfully() throws Exception {
        JobKey jobKey = new JobKey("dailyOrderExport", "order-export");
        scheduler.triggerJob(jobKey);

        await().atMost(Duration.ofSeconds(5))
                .until(() -> orderExportService.wasCalledFor("2026-08-17"));
    }
}
```

This exercises the real `JobFactory` wiring (Part 3.8) and the real `JobDetail`/job-data plumbing — the parts a pure unit test of `OrderExportService` (11.1) doesn't touch at all. `await()` (Awaitility, or an equivalent polling helper) is necessary because `triggerJob()` is asynchronous — it hands the firing off to the scheduler's thread pool and returns immediately, rather than blocking until `execute()` finishes.

### 11.3 Use `RAMJobStore` for tests, even if production uses JDBC

Tests don't need to exercise `JDBCJobStore`'s persistence to verify a job's own logic — that's a separate, narrower concern (11.4). A dedicated test profile keeps the suite fast:

```properties
# application-test.properties
spring.quartz.job-store-type=memory
```

Reserve JDBC-backed tests specifically for verifying persistence and clustering behavior, rather than defaulting every test to the slower, database-backed configuration.

### 11.4 What a persistence/restart test actually verifies

If your production job store is `JDBCJobStore`, it's worth having at least one test that verifies schedules genuinely survive an application restart — since that's the entire point of choosing JDBC over `RAMJobStore` in the first place (Part 5.1), and it's exactly the kind of thing that's easy to assume works without ever having actually checked it:

```
start application → scheduler.scheduleJob(...) → stop application
        → start application again → assert scheduler.checkExists(jobKey) is true
```

### 11.5 Testing the double-fire guard in a cluster

For a clustered deployment, the property actually worth verifying under test is the one clustering exists to guarantee in the first place: a given firing is claimed by exactly one node, not independently executed by every node. Standing up two `Scheduler` instances against the same test database and firing a shared trigger, then asserting the job's business logic recorded exactly one execution (not one per node), is the shape of test that catches a misconfigured cluster before production does.

### 11.6 Proving the JobFactory's per-execution-instance guarantee

Part 3 spends real effort establishing that `AutowiringSpringBeanJobFactory` (3.6) creates a **fresh** job instance on every firing, unlike the flawed singleton-returning version in 3.5. That's exactly the kind of claim worth a test proving directly, rather than trusting the explanation:

```java
@SpringBootTest
class OrderExportJobFactoryTest {

    @Autowired
    private Scheduler scheduler;

    @BeforeEach
    void resetTracking() {
        InstanceTrackingOrderExportJob.reset(); // static state survives across test methods otherwise
    }

    @Test
    void createsANewInstanceOnEveryFiring() throws Exception {
        JobKey jobKey = new JobKey("dailyOrderExport", "order-export");

        scheduler.triggerJob(jobKey);
        await().atMost(Duration.ofSeconds(5)).until(() -> InstanceTrackingOrderExportJob.lastInstance() != null);
        Object firstInstance = InstanceTrackingOrderExportJob.lastInstance();

        scheduler.triggerJob(jobKey);
        await().atMost(Duration.ofSeconds(5))
                .until(() -> InstanceTrackingOrderExportJob.lastInstance() != firstInstance);

        assertThat(InstanceTrackingOrderExportJob.lastInstance()).isNotSameAs(firstInstance);
    }
}
```

(`InstanceTrackingOrderExportJob` here is a small test-only job subclass that records `this` into a static field at the start of `execute()` — a deliberate, test-only exception to the "no static state" instinct, purely to make the instance identity observable from outside. Precisely because it's static, the `@BeforeEach` reset above matters — without it, a previous test method's leftover instance could make `lastInstance() != null` true before this test ever triggers anything, silently passing for the wrong reason.) This test would have caught the exact regression 3.5 walks through as a cautionary example — if the factory silently reverted to returning a shared singleton, `isNotSameAs` would fail immediately, rather than the problem only surfacing later as a subtle concurrency bug under real load.

### 11.7 Testing `@DisallowConcurrentExecution`

The BLOCKED trigger state from Part 2.5 is a real behavior worth verifying directly, not just trusting the annotation to work. As with 11.6's static instance tracking, `SlowExportJob`'s counters are static test-only state, so reset them in a `@BeforeEach` the same way — otherwise a previous test method's leftover count could make `maxObservedConcurrency()` misleading before this test has triggered anything itself:

```java
@Test
void secondFiringWaitsForFirstToComplete() throws Exception {
    JobKey jobKey = new JobKey("slowExportJob", "order-export"); // job sleeps ~2s in execute()

    scheduler.triggerJob(jobKey);
    await().atMost(Duration.ofSeconds(2)).until(SlowExportJob::hasStarted); // wait for an event, not a guessed delay
    scheduler.triggerJob(jobKey); // should be held BLOCKED, not run concurrently

    await().atMost(Duration.ofSeconds(5))
            .until(() -> SlowExportJob.concurrentExecutionCount() <= 1);

    assertThat(SlowExportJob.maxObservedConcurrency()).isEqualTo(1);
}
```

The assertion that matters is `maxObservedConcurrency() == 1` — proving the second firing genuinely waited rather than merely completing successfully, which alone wouldn't rule out having run concurrently and just gotten lucky. Note the deliberate use of `await().until(SlowExportJob::hasStarted)` rather than a fixed `Thread.sleep(...)` to synchronize on the first firing actually starting — a sleep-and-hope delay is exactly the kind of flakiness this guide warns against elsewhere (11.9), and there's no reason to teach it here just because it's a test about timing.

### 11.8 Testing misfire behavior

Misfire policies (2.2) are easy to configure and easy to never actually verify. **This is an illustrative shape for such a test, not a guaranteed-deterministic recipe to copy verbatim** — misfire handling touches the scheduler and job store's internal timing in ways that can behave slightly differently across Quartz versions and job store configurations, so treat the structure below as the concept to adapt rather than a drop-in test:

```java
@Test
void misfiredTriggerFiresOnceOnRecovery() throws Exception {
    scheduler.standby(); // stop firing, without shutting down entirely

    Trigger pastDueTrigger = TriggerBuilder.newTrigger()
            .forJob(jobKey)
            .startAt(Date.from(Instant.now().minus(Duration.ofMinutes(10)))) // already in the past
            .withSchedule(SimpleScheduleBuilder.simpleSchedule()
                    .withMisfireHandlingInstructionFireNow())
            .build();
    scheduler.scheduleJob(pastDueTrigger);

    scheduler.start(); // resume — the past-due fire time is now a misfire Quartz has to handle

    await().atMost(Duration.ofSeconds(5)).until(() -> orderExportService.wasCalledFor(expectedWindow));
    assertThat(orderExportService.callCountFor(expectedWindow)).isEqualTo(1); // exactly one catch-up firing, not zero, not more than one
}
```

`scheduler.standby()` is the tool that makes this test possible — it stops the scheduler from firing anything without fully shutting it down, which is what creates a deliberate, controllable "missed fire time" window to test against, rather than needing to actually wait out a real outage. The concept that matters, regardless of the exact mechanics your Quartz version uses to get there: create an overdue trigger → let the scheduler process it → assert the misfire instruction's expected firing count, no more and no less.

### 11.9 Common pitfalls

| Symptom | Cause | Fix |
|---|---|---|
| Test passes locally but the job fails in real deployment on first fire | Test constructs the job directly (`new OrderExportJob(mockService)`), bypassing the real `JobFactory` entirely | Add at least one test that goes through the real scheduler (11.2), not just direct construction |
| Tests are slow | Using `JDBCJobStore` (often against a real or containerized DB) for tests that don't need persistence at all | Use `spring.quartz.job-store-type=memory` for anything that isn't specifically testing persistence (11.3, 11.4) |
| Integration test is flaky | Asserting immediately after `triggerJob()` without waiting — firing is asynchronous | Poll with a timeout (`await()` or equivalent) instead of asserting synchronously right after the call |

## Part 12 — Listeners

### 12.1 The three listener interfaces

Listeners are Quartz's hook mechanism for observing what the scheduler is doing without touching the job class itself. Three interfaces, each scoped to a different level:

| Interface | Scope | Typical use |
|---|---|---|
| `JobListener` | A job's execution lifecycle | Metrics, cleanup, audit logging around a job run |
| `TriggerListener` | A trigger's firing lifecycle | Vetoing a firing, alerting on misfires |
| `SchedulerListener` | The scheduler itself | Startup/shutdown hooks, cluster/error events |

The key design point: **listeners are registered at runtime with the `Scheduler`'s `ListenerManager`, and are never persisted to the job store.** Unlike a `JobDetail` or `Trigger`, a listener isn't a row in `QRTZ_JOB_DETAILS` — it's a plain Java object handed to the scheduler each time your application starts. This is exactly why they're a good fit for cross-cutting concerns like metrics: they live entirely in your application's wiring, with no schema or persistence implications at all.

### 12.2 `JobListener`

```java
public interface JobListener {
    String getName();
    void jobToBeExecuted(JobExecutionContext context);
    void jobExecutionVetoed(JobExecutionContext context);
    void jobWasExecuted(JobExecutionContext context, JobExecutionException jobException);
}
```

- `jobToBeExecuted` — fires immediately before `Job.execute()`.
- `jobExecutionVetoed` — fires instead of execution, if a `TriggerListener` vetoed this firing (12.3).
- `jobWasExecuted` — fires immediately after `Job.execute()` returns, whether it succeeded or threw. `jobException` is `null` on success.

A minimal example that emits a metric on every export job failure, without `OrderExportJob` itself knowing anything about a metrics system:

```java
@Component
public class ExportJobMetricsListener implements JobListener {

    private final MeterRegistry meterRegistry;

    public ExportJobMetricsListener(MeterRegistry meterRegistry) {
        this.meterRegistry = meterRegistry;
    }

    @Override
    public String getName() {
        return "exportJobMetricsListener";
    }

    @Override
    public void jobToBeExecuted(JobExecutionContext context) {
        // no-op — nothing to record before execution starts
    }

    @Override
    public void jobExecutionVetoed(JobExecutionContext context) {
        meterRegistry.counter("orderexport.quartz.job.vetoed",
                "job", context.getJobDetail().getKey().getName()).increment();
    }

    @Override
    public void jobWasExecuted(JobExecutionContext context, JobExecutionException jobException) {
        String outcome = jobException != null ? "failure" : "success";
        meterRegistry.counter("orderexport.quartz.job.completed",
                "job", context.getJobDetail().getKey().getName(),
                "outcome", outcome).increment();
    }
}
```

### 12.3 `TriggerListener`

```java
public interface TriggerListener {
    String getName();
    void triggerFired(Trigger trigger, JobExecutionContext context);
    boolean vetoJobExecution(Trigger trigger, JobExecutionContext context);
    void triggerMisfired(Trigger trigger);
    void triggerComplete(Trigger trigger, JobExecutionContext context, Trigger.CompletedExecutionInstruction triggerInstructionCode);
}
```

The one method worth pausing on is `vetoJobExecution`: return `true` and the job never runs at all — `jobExecutionVetoed` fires on any registered `JobListener` instead. This is the mechanism for "should this even attempt to run" business rules (e.g. a feature-flag check, an environment guard) that shouldn't live inside `OrderExportJob`'s own `execute()`.

`triggerMisfired` is the one most directly useful in practice: it fires whenever a trigger's fire time passed without actually firing (2.2) — independent of whether you chose `FireAndProceed` or `DoNothing` as the misfire instruction. That makes it the natural place to alert on misfires, regardless of how each trigger recovers from one:

```java
@Component
public class ExportTriggerMisfireListener implements TriggerListener {

    private static final Logger log = LoggerFactory.getLogger(ExportTriggerMisfireListener.class);
    private final AlertPublisher alertPublisher;

    public ExportTriggerMisfireListener(AlertPublisher alertPublisher) {
        this.alertPublisher = alertPublisher;
    }

    @Override
    public String getName() {
        return "exportTriggerMisfireListener";
    }

    @Override
    public void triggerMisfired(Trigger trigger) {
        log.warn("Trigger misfired: {}", trigger.getKey());
        alertPublisher.publish("Quartz trigger misfired: " + trigger.getKey());
    }

    @Override
    public void triggerFired(Trigger trigger, JobExecutionContext context) {
        // no-op
    }

    @Override
    public boolean vetoJobExecution(Trigger trigger, JobExecutionContext context) {
        return false; // never veto — this listener only observes
    }

    @Override
    public void triggerComplete(Trigger trigger, JobExecutionContext context,
            Trigger.CompletedExecutionInstruction triggerInstructionCode) {
        // no-op
    }
}
```

### 12.4 `SchedulerListener`

Scheduler-level events: `schedulerStarted`, `schedulerShuttingdown`, `jobScheduled`, `jobDeleted`, `schedulerError`, and several more. `schedulerError` is the one most worth wiring up in production — it fires for scheduler-internal failures (e.g. the JDBC job store failing to acquire its own lock) that never reach a `Job` or `Trigger` listener, because they're not tied to any specific job firing at all.

### 12.5 Registering listeners: matchers and scope

Listeners are registered against a `Matcher`, which determines which jobs or triggers they receive events for. The two you'll use almost exclusively:

```java
import static org.quartz.impl.matchers.GroupMatcher.jobGroupEquals;
import static org.quartz.impl.matchers.KeyMatcher.keyEquals;

// Scoped to every job in one group
scheduler.getListenerManager().addJobListener(metricsListener, jobGroupEquals("order-export"));

// Scoped to one specific job
scheduler.getListenerManager().addJobListener(metricsListener, keyEquals(new JobKey("DAILY-SUMMARY", "order-export")));

// No matcher at all = every job, scheduler-wide
scheduler.getListenerManager().addJobListener(metricsListener);
```

A group split like this is common in systems with more than one kind of scheduled work — say, order-export jobs living in an `order-export` group, and separate maintenance jobs (failed-export retries, data retention) living in their own `order-maintenance` group specifically so cleanup or monitoring logic never has to reason about them together. `jobGroupEquals("order-export")` scopes a listener to just the export jobs, without it ever seeing maintenance-job firings — the listener-matcher mechanism is what makes that separation enforceable, not just a naming convention.

### 12.6 Wiring listeners into a Spring Boot scheduler

Spring's `SchedulerFactoryBean` exposes `setGlobalJobListeners(JobListener...)`, `setGlobalTriggerListeners(TriggerListener...)`, and `setSchedulerListeners(SchedulerListener...)` directly — so listeners slot into the exact same `SchedulerFactoryBeanCustomizer` pattern already established for the `JobFactory` in Part 3.8, rather than needing a new wiring mechanism:

```java
@Bean
public SchedulerFactoryBeanCustomizer listenerCustomizer(
        ExportJobMetricsListener metricsListener,
        ExportTriggerMisfireListener misfireListener) {
    return schedulerFactoryBean -> {
        schedulerFactoryBean.setGlobalJobListeners(metricsListener);
        schedulerFactoryBean.setGlobalTriggerListeners(misfireListener);
    };
}
```

"Global" here means no matcher — every job/trigger in the scheduler. If you need the group-scoped behavior from 12.5 instead, register directly against the `Scheduler` bean's `ListenerManager` (e.g. from an `ApplicationRunner`) rather than through `SchedulerFactoryBean`'s global setters, which don't accept a `Matcher`.

### 12.7 Keep listener code fast, and handle your own exceptions

Two production rules worth stating explicitly, since nothing about the listener interfaces themselves enforces either one.

**Listener methods run inline in the scheduling/execution path, not off on some conveniently separate background thread — the exact threading details can vary by job store, but the practical implication doesn't.** `jobToBeExecuted` runs immediately before `execute()`; `triggerFired` runs as part of the firing sequence itself. A slow database query, a network call, or heavy computation inside a listener directly delays the job it's attached to — and for a `TriggerListener` shared across many triggers, it delays *every* firing that listener observes, not just one. Keep listener bodies to the fast, local work they're suited for (incrementing a counter, logging, publishing an already-prepared event) and hand anything slower off to something else — a queue, an async event, a separate thread — rather than doing it inline.

**An exception thrown from inside a listener method is your problem to handle, not Quartz's.** Listener methods that throw can interfere with other registered listeners for the same event, and with the job execution itself, depending on which method and when. Wrap risky logic in the listener's own try/catch rather than letting it propagate — a bug in a metrics listener has no business taking down (or corrupting the state of) the job it's merely observing.

### 12.8 Common pitfalls

| Symptom | Cause | Fix |
|---|---|---|
| Listener never fires | Registered against the wrong `Scheduler` instance, or after jobs already started firing | Register via `SchedulerFactoryBeanCustomizer` (runs before `start()`), not in a post-startup hook |
| Listener fires for jobs you didn't expect | Used a global listener (`addJobListener(listener)`, no matcher) instead of a group/key matcher | Scope with `jobGroupEquals(...)` or `keyEquals(...)` |
| `triggerMisfired` never fires | Misfire instruction is set to something that resolves instantly without a detectable gap (rare), or the scheduler was never actually down long enough to cross the misfire threshold | Confirm `org.quartz.jobStore.misfireThreshold` (5.x) against your actual outage duration |
| Metrics double-counted in a cluster | Each clustered node registers its own listener instance | Listeners are local to each scheduler instance — a listener registered on Node A does not observe executions performed by Node B. Only the node that actually executes a given firing has its local listener invoked for that execution, which is usually what you want; don't architect around an assumption that every node's listener fires for every job |
| A slow listener noticeably delays job firing or other listeners | Expensive work (I/O, computation) running directly inside a listener method | Move the slow work out of the listener — publish an event or hand off to an async mechanism instead |

## Part 13 — Calendars

### 13.1 What a Quartz `Calendar` is

`org.quartz.Calendar` (not `java.util.Calendar` — the name collision trips people up constantly) is an **exclusion mechanism** attached to a trigger. It doesn't define *when* to fire — that's still the trigger's job (cron expression, interval, whatever). A `Calendar` instead defines time ranges that should be **skipped** even if the trigger's own schedule would otherwise fire during them.

```java
public interface Calendar {
    boolean isTimeIncluded(long timeStamp);
    long getNextIncludedTime(long timeStamp);
    // ...
}
```

When a trigger's next fire time falls on an excluded moment, Quartz doesn't fire it late and doesn't treat it as a misfire (2.2) — it simply computes the *next* included fire time and uses that instead, as part of ordinary schedule computation. Exclusion and misfiring are two entirely different mechanisms that happen to produce a superficially similar symptom ("the trigger didn't fire when I expected") — worth keeping distinct when debugging.

### 13.2 Built-in implementations

| Class | Excludes |
|---|---|
| `HolidayCalendar` | Specific individual dates you add one at a time — the one you'll use for holidays |
| `DailyCalendar` | A recurring time-of-day window, every day (e.g. "never between 00:00–02:00" for maintenance) |
| `WeeklyCalendar` | Specific days of the week entirely (e.g. exclude all of Saturday/Sunday) |
| `MonthlyCalendar` | Specific days of the month (e.g. exclude the 1st) |
| `AnnualCalendar` | Specific dates, recurring every year regardless of year (e.g. Dec 25 every year without re-adding it annually) |
| `CronCalendar` | Any cron-expressible exclusion window |

For a fixed list of bank holidays that changes once a year, `HolidayCalendar` is almost always the right choice over `AnnualCalendar` — holidays like Easter or Thanksgiving don't fall on the same date every year, so a true "same date annually" calendar doesn't fit; you're better off loading a maintained list of actual dates.

### 13.3 Building and registering a `Calendar`

```java
@Bean
public HolidayCalendar warehouseClosures() {
    HolidayCalendar calendar = new HolidayCalendar();
    calendar.setTimeZone(TimeZone.getTimeZone("America/New_York"));
    calendar.addExcludedDate(Date.from(LocalDate.of(2026, 12, 25)
            .atStartOfDay(ZoneId.of("America/New_York")).toInstant()));
    calendar.addExcludedDate(Date.from(LocalDate.of(2026, 1, 1)
            .atStartOfDay(ZoneId.of("America/New_York")).toInstant()));
    return calendar;
}
```

Recall from Part 3.8's look at `QuartzAutoConfiguration` source that the autoconfigured `quartzScheduler()` bean method takes a `Map<String, Calendar> calendars` parameter — Spring Boot auto-detects every `Calendar` bean in your context the same way it auto-detects `JobDetail` and `Trigger` beans, and registers each one under its **bean name** (`warehouseClosures` above becomes the calendar's registered name). No customizer needed for registration itself — `Calendar` beans are on the auto-detected list, unlike `JobFactory`.

**The timezone matters more than it looks.** `HolidayCalendar.setTimeZone()` controls which timezone "midnight" is computed against for each excluded date. If it doesn't match the timezone your triggers are built with (the `.inTimeZone(...)` call on the trigger itself), an excluded date can silently apply to the wrong local day — a trigger firing at 11pm Dec 24 in one timezone might read as Dec 25 in another, and either get excluded when it shouldn't or fire when it shouldn't. Keep the calendar's timezone and the trigger's `.inTimeZone(...)` in lockstep.

### 13.3a Chaining calendars together

A single trigger can only be attached to one calendar via `modifiedByCalendar` (13.4) — but that one calendar doesn't have to represent only one kind of exclusion. Every `Calendar` implementation supports a **base calendar**, chaining one calendar's exclusions on top of another's:

```java
@Bean
public WeeklyCalendar weekends() {
    WeeklyCalendar calendar = new WeeklyCalendar();
    calendar.setDayExcluded(Calendar.SATURDAY, true);
    calendar.setDayExcluded(Calendar.SUNDAY, true);
    return calendar;
}

@Bean
public HolidayCalendar warehouseClosures(WeeklyCalendar weekends) {
    HolidayCalendar calendar = new HolidayCalendar();
    calendar.setTimeZone(TimeZone.getTimeZone("America/New_York"));
    calendar.addExcludedDate(/* ... specific holiday dates ... */);
    calendar.setBaseCalendar(weekends);  // chain: exclude holidays AND weekends
    return calendar;
}
```

A time is excluded if *either* the calendar itself excludes it *or* its base calendar does — and base calendars can chain further (a base calendar can itself have a base calendar), so a trigger can effectively observe several independent exclusion rules — weekends, fixed holidays, a recurring daily maintenance window — while `modifiedByCalendar` still only ever references the one, outermost calendar name. This is the mechanism for "exclude weekends *and* holidays" without hand-merging both sets of dates into a single `HolidayCalendar`.

### 13.4 Attaching a calendar to a trigger

Registering a `Calendar` with the scheduler doesn't apply it to anything by itself — each trigger opts in individually:

```java
Trigger trigger = TriggerBuilder.newTrigger()
        .forJob(jobDetail)
        .withIdentity(identity + "-trigger", TRIGGER_GROUP)
        .withSchedule(CronScheduleBuilder.cronSchedule(schedule.getCron())
                .inTimeZone(TimeZone.getTimeZone(timezone))
                .withMisfireHandlingInstructionFireAndProceed())
        .modifiedByCalendar("warehouseClosures")   // ← the bean name from 13.3
        .build();
```

`modifiedByCalendar` takes the calendar's registered name as a plain string, not a bean reference — there's no *compile-time* check tying a trigger to a calendar that actually exists. That doesn't mean a typo goes unnoticed forever, though: Quartz validates the referenced calendar's existence when the trigger is actually stored/scheduled, so a name that doesn't match anything registered surfaces as a runtime scheduling error at that point, not a silent no-op that only shows up later as "the trigger never seems to skip holidays." Still worth a dedicated integration test that exercises the real scheduling call with the real calendar name, rather than assuming a string literal typed correctly once will always match — but the failure mode is "loud at schedule time," not "silent forever."

### 13.5 A worked example: skipping order exports on warehouse closure days

Extending the trigger-building shape from Part 8.1's `exportTrigger()` bean method to conditionally apply the holiday calendar, without touching any maintenance-job triggers, which have no reason to observe warehouse closures:

```java
@Bean
public Trigger exportTrigger(JobDetail exportJobDetail, @Value("${export.observes-holidays}") boolean observesHolidays) {
    TriggerBuilder<CronTrigger> builder = TriggerBuilder.newTrigger()
            .forJob(exportJobDetail)
            .withIdentity("dailyOrderExport-trigger", "order-export")
            .withSchedule(CronScheduleBuilder.cronSchedule("0 0 6 * * ?")
                    .inTimeZone(TimeZone.getTimeZone("America/New_York"))
                    .withMisfireHandlingInstructionFireAndProceed());

    if (observesHolidays) {
        builder.modifiedByCalendar("warehouseClosures");
    }
    return builder.build();
}
```

This keeps the holiday decision a runtime configuration choice (`export.observes-holidays`) rather than baked into the cron expression itself — which would otherwise require hand-encoding holiday exclusions into `day-of-month`/`month` cron fields, an approach that doesn't scale past a handful of fixed dates and breaks the moment a holiday list changes year to year. In a schedule with many export triggers built from a shared builder method rather than one-off `@Bean`s like this, the same `if (observesHolidays)` branch applies per-trigger, driven by whatever configuration source that builder reads from.

### 13.6 Common pitfalls

| Symptom | Cause | Fix |
|---|---|---|
| Trigger fires on an excluded date anyway | Trigger never called `.modifiedByCalendar(...)`, or used the wrong registered name | Confirm the bean name matches the string passed to `modifiedByCalendar` exactly |
| Excluded date off by one day | Calendar's timezone doesn't match the trigger's `.inTimeZone(...)` | Set `calendar.setTimeZone(...)` to the same zone used when building the trigger |
| Calendar bean not applied at all | Bean type isn't exactly `org.quartz.Calendar` (or a direct implementation) — Spring Boot's auto-detection keys off that type | Confirm the `@Bean` method's return type is a `Calendar` implementation, not a wrapper or `Object` |
| Holidays need updating every year | Using `HolidayCalendar` with dates hardcoded in Java rather than loaded from config/a maintained source | Externalize the date list so it doesn't require a redeploy each January |

## Production Rules of Thumb

A compact summary of the judgment calls this guide has argued for at length, useful as a final gut-check rather than a substitute for the reasoning behind each one:

1. **Keep jobs thin.** Business logic lives in Spring services; `execute()` translates Quartz's context into a call against them (Part 3.7).
2. **Don't store Spring beans, entities, or large object graphs in `JobDataMap`.** It's small scheduling metadata, not an application state store (Part 10 note in 7.2's `@PersistJobDataAfterExecution` example).
3. **Assume every job can run more than once for the same logical work, and make it idempotent** (Part 10.1-10.2) — via misfire catch-up, cluster recovery, a manual re-trigger, or plain human error.
4. **Recovery, retry, and misfire are three different mechanisms** that can all produce a repeat execution — know which one you're looking at (Part 10.4).
5. **Use explicit timezones everywhere** — trigger schedules, calendars, and DST behavior (Part 13, "Where to go from here") all depend on getting this right, not on assuming a server default.
6. **Treat a misfire policy as a business decision**, not a default to leave untouched (Part 2.2) — "catch up" and "skip" are both legitimate, and the right choice depends on the job.
7. **Decide explicitly whether code or the database owns a given schedule**, and set `overwrite-existing-jobs` accordingly (Part 5.5) — don't enable it reflexively.
8. **Test the restart and cluster-double-fire cases**, not just the happy path (Part 11.4-11.5) — these are exactly the properties that are easy to assume work without ever having checked.
9. **Size the Quartz thread pool and datasource together, from measured load** — not from a number copied out of a tutorial (Part 5.4, Part 8).
10. **Never hand-edit `QRTZ_*` tables directly** — the `Scheduler` API is the only supported way to change scheduling data (Part 5.3).
11. **Don't assume clustering means workload-aware load balancing** — it's automatic and roughly random, not CPU- or queue-depth-aware (Part 6.2).
12. **Never let an untrusted caller submit an arbitrary job class or unvalidated `JobDataMap`** if you expose dynamic scheduling (Part 9) through any kind of UI or API.

## Where to go from here

This guide covers what's needed to run Quartz confidently in a real Spring Boot application — but it's not a complete reference for every corner of Quartz. A few topics worth knowing exist, deliberately left out to keep this guide focused:

- **Plugins** — Quartz's own scheduler-level extension mechanism (e.g. `ShutdownHookPlugin`), distinct from jobs/triggers, and rarely load-bearing in a Spring Boot app since Spring's own lifecycle callbacks usually cover the same ground.
- **The Spring Batch + Quartz boundary** — when Quartz should only trigger *when* a Spring Batch job starts versus when Quartz itself should own more of the work directly. This is ultimately a design judgment call for your specific system, not a fixed rule this guide can hand you.
- **`JobStoreTX` vs `JobStoreCMT`** — this guide uses `JobStoreTX` throughout (Quartz manages its own transactions against its dedicated `DataSource`, Part 5.4). `JobStoreCMT` is the alternative for coordinating Quartz's persistence within a container/application-managed transaction instead — relevant if your application's transaction model requires that level of coordination, which most Spring Boot + `JobStoreTX` setups don't.
- **`@QuartzTransactionManager`** — if Quartz genuinely needs a different `PlatformTransactionManager` than your application's primary one, Spring Boot supports designating one specifically for Quartz via this annotation.
- **Cluster clock synchronization** — clustering (Part 6) depends on nodes agreeing on time closely enough for check-in intervals and lock timeouts to behave sensibly. Don't assume this for free — ensure NTP (or equivalent) keeps every clustered node's clock synchronized; don't rely on application-level time coordination to paper over drifting system clocks.
- **`batchTriggerAcquisitionMaxCount`/`batchTriggerAcquisitionFireAheadTimeWindow`** — for schedulers with a very large number of triggers, Quartz can acquire several triggers per polling cycle instead of one at a time. Worth knowing this tuning knob exists if trigger-acquisition throughput becomes a bottleneck; not something a typical schedule needs to touch.
- **`maxMisfiresToHandleAtATime`** — bounds how many missed triggers Quartz processes in a single misfire-handling pass, so a large backlog of misfires (e.g. after extended downtime) doesn't hold database locks for an extended stretch and starve other triggers. Worth knowing about if you operate a schedule where extended outages are plausible.
- **Timezones and Daylight Saving Time** — a `CronTrigger` firing at a fixed local time (e.g. `02:30` daily) can behave unexpectedly across a DST transition — the time can be skipped entirely during a "spring forward" gap, or occur twice during a "fall back" repeat. `SimpleTrigger`, by contrast, isn't affected the same way, since it operates on elapsed milliseconds rather than a local wall-clock time. If a schedule's exact local behavior across a DST boundary matters for your use case, verify it explicitly against your target timezone rather than assuming `CronTrigger` handles it the way you'd intuitively expect.
- **Authorization for dynamic scheduling** — if you build an admin panel or API around Part 9's dynamic scheduling capabilities, never let an untrusted caller submit an arbitrary Quartz job class or unvalidated `JobDataMap` contents directly. Constrain user input to a known, server-validated set of schedule types and parameters — a job class name accepted from user input is a code-execution risk, not just a scheduling one.
- **Quartz's `CalendarIntervalTrigger` and `DailyTimeIntervalTrigger`** — two more built-in trigger types beyond `SimpleTrigger`/`CronTrigger` (Part 2.1), for calendar-aware intervals (e.g. "every 2 months, respecting varying month lengths") and daily time-window repetition, respectively. Worth knowing they exist if `SimpleTrigger`/`CronTrigger` don't quite fit a given schedule's shape.
- **JMX and scheduler metrics** — Quartz exposes scheduler and job execution details via JMX for external monitoring; this guide's Part 12 listener-based approach (application-level metrics via `MeterRegistry`) covers similar ground from inside your own application instead.
